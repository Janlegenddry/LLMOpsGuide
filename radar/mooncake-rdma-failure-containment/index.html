结论

官方事实[1] ↗[2] ↗[3] ↗[4] ↗

Mooncake 在今天合入了两项值得进入升级评估的修复：TENT RDMA 完成阶段的元数据所有权修复，以及 Transfer Engine 握手写入的 SIGPIPE 抑制。二者共同回答一个运维问题：对端变化或异步延迟发生后，错误能否留在可处理的边界内。

推导 / 教学示例

建议先核对线上实际构建的源码，再建立带故障注入的候选版本验证。今天的新事实是主干合入，不能写成正式版本已经提供修复。两项变更也没有证明请求自动重试、KV 数据一致性或整组服务恢复已经完成。

推导 / 教学示例

以下机制结论来自固定提交源码；实验及上线标准是本文提出的验证方案，均未在本次核验中实际执行。未获得 H20、真实 RDMA 网络或推理框架集成的测试结果。

增补：空闲 TCP 连接边界

推导 / 教学示例[19] ↗[20] ↗

10 月 9 日增补：#4234 处理空闲 TCP lane 的对端关闭检测；它与前文 RDMA 标识所有权、握手 SIGPIPE 分属不同边界。源码合入不等于正式 wheel 已包含，连接可重建也不等于本次业务请求已恢复。

背景与发布边界

推导 / 教学示例

RDMA 请求提交和完成处理分属不同时间点；完成回调依赖的对象，必须覆盖这段异步间隔。握手服务则同时面对正常连接、突然断开的连接和停止读取的连接。把这些情况都归入“网络异常”，容易漏掉进程退出、内存生命周期和阻塞时限这三种不同问题。

机制与故障隔离

RDMA 元数据的有效期

官方事实[3] ↗

#4437 将 slice 中的源 NIC 名、目标 NIC 名和目标 machine ID 改为持有值。generatePostPath 在每次提交路径生成时复制标识，完成处理使用这些副本；元数据快照替换不再决定这些标识的存活期。该修改针对 GDR 可达性上报所用的元数据，不代表数据缓冲区、注册内存或 endpoint 的全部生命周期都已重新验证。固定提交

推导 / 教学示例

工程上的重点是分别检查“当前路由是什么”和“这次已提交操作使用过什么”。对在途操作的归因应绑定提交时的信息，否则刷新配置本身就可能破坏诊断或恢复动作。建议日志保留提交尝试 ID，将重试产生的新归因与旧完成事件区分开。

握手错误返回的边界

官方事实[4] ↗

#4463 新增 socket 专用写入函数，Linux 使用 MSG_NOSIGNAL，macOS 使用 SO_NOSIGPIPE；writeString 转用该函数。EINTR 重试，EAGAIN/EWOULDBLOCK 返回已写字节数，由上层完整长度检查判失败。原文件写入函数保持独立。固定提交及完整补丁

推导 / 教学示例

必须继续区分三个条件：进程没有因信号退出、失败能在时限内返回、业务能够再次成功。第一项成立不能替代后两项。尤其“有超时返回分支”并不等于当前 socket 已设置发送超时。

当前主干仍需单独核对的时限

官方事实[12] ↗

在 9f4c206 的握手实现里，接收端设置了 SO_RCVTIMEO，未见 SO_SNDTIMEO；writeString 既用于服务端应答，也用于主动连接的请求。不能把影响面简化为只覆盖 accept 得到的 socket。固定握手实现

官方事实[13] ↗

发送停滞的专门变更 #4451 在本次核验时仍为 OPEN。本文不把它算入今天已合入的保证。发送停滞 PR

增补机制：复用前探测，不消费字节

官方事实[20] ↗

固定代码在复用 IDLE lane 前做非阻塞 Asio receive(message_peek)。只有 received=0 且 would_block/try_again 才继续；否则重置 socket、置 DISCONNECTED、清 last_connect_round 并 continue。后续 pump 轮次按既有状态与预算处理重连。

收益与代价

推导 / 教学示例

本次最直接的潜在收益是缩小故障扩散范围。运维上应关注因异常导致的进程重启、健康流量受阻和错误归因，而不只盯平均带宽。故障被正常返回后，如果调用方立即无界重试，仍可能把原来的崩溃变成重试风暴。

推导 / 教学示例

拥有字符串会引入复制和生命周期管理成本。不能凭字符串短就宣布成本可以忽略；高 slice 速率下，建议同时看 CPU 使用、分配行为和尾延迟。ASan 构建用于暴露生命周期问题，正式优化构建用于比较性能，两个数据集应单独记录。

推导 / 教学示例

握手失败更可见之后，错误日志量也可能变化。应按目标与错误类型聚合，并保留速率限制，避免一次故障让日志吞吐成为新的瓶颈。部署策略上，优先做单组 canary，保留可回滚镜像和精确依赖清单。

推导 / 教学示例

强制 TCP 的空闲连接试验与 RDMA 所有权试验应独立。peek 不等于心跳、不提供统一恢复秒数，也不完成上层请求账本。连续请求正常只能作为对照，不能替代主动关闭对端与空闲后重入的故障检查。

生产落地顺序

推导 / 教学示例

第一步确定实际运行路径。记录 Mooncake 版本、构建提交、是否使用 TENT RDMA，以及握手插件和上层调用者。框架的版本号不足以说明链接了哪份传输库；SGLang 或其他服务的镜像需要单独检查，不能由上游 main 推导其包含修复。

推导 / 教学示例

第二步形成候选构建。保留原版本、只加入元数据修复、只加入握手修复、联合修复四组基线，以便定位收益和回归。若选择 cherry-pick，必须重新验证依赖上下文；“补丁可以应用”不是行为等价证明。

推导 / 教学示例

第三步建立观测链。把请求 ID、传输批次、对端身份、失败类型和重试次数关联起来。分别记录进程存活、握手返回、传输结果和用户请求完成，避免把错误日志消失当成成功。

推导 / 教学示例

第四步再做真实硬件验收。H20 部署要使用实际驱动、CUDA、NIC 固件、拓扑和内存注册方式。这里的源码修改没有提供 H20 性能提升、兼容性认证或显存用量改善的直接证据。

推导 / 教学示例

新增可反驳假设：故障来自复用对端已关闭的空闲 TCP socket。需要同时记录 lane/socket 状态、peek 结果、丢弃时点、后续 pump 与新连接、提交结果和 vLLM 请求状态。若 group 已 CLOSED 或工作在 lane 之前被拒绝，应转向组退休与准入路径，不能用本修复替代根因分析。

官方事实[23] ↗

#4451 本轮公开状态仍为 open、merged=false；发送停滞的时限边界没有因 #4234 的空闲重连而自动闭合。
