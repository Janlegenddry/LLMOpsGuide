KV Cache / 故障分析

Mooncake P/D 固定字节为何仍变慢：descriptor 形状、提交边界与真实流量验收

原文 2026-11-14核对 2026-11-20

相同 752 MiB/rank 的 KV，描述符可以从 94 条变成 96,256 条。本文区分降序归一化、slice/WR 与 classic TE arrays 三类机制，核对版本和统计边界，并给出真实流量之前应完成的诊断与灰度门禁。

一、结论：KV 字节没增加，P/D 也可能因为元数据工作变慢

推导 / 教学示例

值得加入推理 SRE 排障手册的新分支是：在每 rank 传输字节近似不变时，检查 descriptor 数、首次发包延迟和提交入口，而不是直接给网络加带宽。它可以成为一项可复用的诊断能力，但目前证据来自公开 vLLM/Mooncake 实验，不是任何本地 SGLang、昇腾或业务集群已经命中的故障。

推导 / 教学示例

这不是一个优化解决三个问题。共同降序归一化减少可合并场景的 descriptor；slice 调整改变单个 descriptor 内的切分；classic TE arrays 减少 Python/C++ 边界转换。它们分别作用于布局、WR 粒度和提交表示，不能用“KV 传输优化”四个字混为一谈。

官方事实[1] ↗[2] ↗[4] ↗

#63142 已合入且在 v0.34.0 冻结 sender 中可见归一化助手；#67656 于 11 月 16 日合入，但 v0.34.0 sender 仍调用 legacy list 接口。报告核对日期为 11 月 20 日，并非宣布当天发布新版本。

推导 / 教学示例

推荐先做隔离环境的观测和回归，再通过另行授权的真实流量灰度验证收益。只升级 Mooncake 包、只看平均 KV 带宽、或只证明合成请求跑通，都不够作为生产推广依据。

二、背景：传同一批数据，为什么“搬运清单”能差三个数量级

作者报告结果[3] ↗

descriptor 是源地址、目标地址和长度组成的搬运描述。一个大的连续片段可以用一条清单项表达，散成许多小片段则需要许多项。TE 再将清单项切成 slice，形成 RDMA 工作请求 WR。字节相同并不保证描述符数量相同，更不保证 CPU 准备、提交与完成记账的成本相同。

作者报告结果[3] ↗

作者的固定字节调查采用 Qwen3-235B-A22B BF16、两台各 8×H20、1P1D TP8。在 16K 工作负载里，每 rank/API 调用均传 752 MiB，却同时出现 94×8 MiB 与 96,256×8 KiB 两种清单形状。以下数据都是该实验的 rank 级调用均值，不是端到端 p99。

推导 / 教学示例

诊断时要分开两种“带宽”：链路/NIC 的数据吞吐，以及 bytes÷同步 API 墙钟时间得到的有效传输速率。后者包含准备和等待，下降可能发生在 NIC 还没开始工作之前。反过来，API 变快也不保证业务首 token 更快，因为 P 排队、计算、D 等待仍可能支配关键路径。

三、机制：减少项数、调整切片、换提交表示，互不替代

推导 / 教学示例[2] ↗[4] ↗

降序归一化保持每个源块与目标块配对，只翻转两边同时连续递减的区间。教学例中 P=[3,2,1]、D=[10,9,8] 可以同时反转为 P=[1,2,3]、D=[8,9,10]；映射不变，后续才有机会按物理连续性合并。若 P 递减而 D 递增，任意独立排序会破坏映射，不能为了减少 descriptor 强行这么做。

官方事实[2] ↗[4] ↗

归一化发生在逻辑块展开前。一个逻辑块对应多个 kernel block 时，先展开可能把原来的共同降序结构拆散；先归一化再展开能保留可合并机会。但跨 region、KV 组和布局是否允许连续搬运，仍由后续规则约束，不能仅凭数字 ID 相邻判断。

推导 / 教学示例

slice 是每项内部的切片上限，不是跨项合并器。把上限从 64 KiB 提到 1 MiB 可以减少 8 MiB descriptor 的 WR；原本每项只有 8 KiB 的清单仍逐项存在。先测 descriptor 形状，再决定是否值得测 slice，比先改参数再解释结果更可靠。

官方事实[7] ↗

新接口的同步批次结果也有严格含义：COMPLETED 表示所有 range 成功；FAILED 不表示所有 range 都失败；num_ranges 不是成功范围计数。输入数组要求等长、一维、连续的 native uint64，并在调用期间保持稳定。性能接入不能顺手改变错误处理和缓冲区生命周期。

官方事实[6] ↗

TE 实现通过 callable 检查选择数组写 API；缺失或不可调用时回退列表。因而需要同时核对 connector 代码、Mooncake 后端与实际命中的 API。包里存在方法和请求真正走新路径，是两条不同的证据。

五、取舍：为什么 16K 的漂亮结果到 32K 不一定成立

作者报告结果[8] ↗

作者跟进解释：32K、APC 关闭且 P 饱和时，P 为在传请求保留块，D 更早释放并复用；下一请求两侧的分配方向可能不同。其观察中 94 与 192,512 descriptor 调用交替，归一化只处理共同方向，不能改变两侧分配器生命周期。

推导 / 教学示例

同一跟进在特定 APC 开启实验中不再观察到该周期，不等于“开 APC 就能解决描述符问题”。APC 同时可能改变传输字节、命中率、驻留时间和排队。将它作为对照因素，而不是未经验证的生产处方。

作者报告结果[2] ↗[8] ↗

该 32K 实验的 P 侧排队已经把 TTFT 推到百秒量级。削减几十或数百毫秒的传输，并不会自动消除队列。应先判断关键路径由谁支配：布局/提交、链路进展，还是 P/D 容量不匹配。

推导 / 教学示例
  • arrays 不是“零拷贝”，也不减少 descriptor 或 WR 数；仍需 bulk copy，且输入生命周期不可随意放松。
  • 本文实验针对 classic TE RDMA。相邻 TENT 工作不能作为此处收益证据；更不能由 vLLM connector 的实现推断 SGLang 或 vLLM-Ascend 同样受益。
  • 更大 slice 会改变 RDMA 工作粒度，评估时还应看并发公平性、资源压力和故障恢复，不能只看一个大请求的均值。
  • 数据传输改善可能被 CPU 抢占、NUMA/HCA 放置或 P 侧排队抵消。对照必须固定硬件与负载，而不是跨节点拼接漂亮结果。

八、验收：先证明没有失真，再认领容量或成本收益

官方事实[5] ↗

冻结统计定义中，P 侧暴露 vllm:mooncake_num_descriptors、vllm:mooncake_bytes_transferred 与 vllm:mooncake_xfer_time_seconds；最高有限 descriptor 桶为 50,000。96,256 与 192,512 都在该桶之外，仅凭这组桶不能区分两者。

推导 / 教学示例

可用 count 增量减去 le=50000 桶增量估计大于 50k 的成功传输占比，再除以同一标签/窗口的 count 增量；零样本时不计算比例。具体标签和桶值格式以运行端导出为准。精确区分 96k/192k 需要关联采样或评估新增桶，不能让 histogram_quantile 凭空恢复不存在的分辨率。

九、未验证与下一步：形成诊断资产，不急着改生产参数

待验证[1] ↗[4] ↗[10] ↗
  • 本文是 11 月 20 日对公开证据的原创解读；核心 PR 的创建/合入日期更早，不伪装为今日发布。未执行 GPU、RDMA、精度、吞吐或生产灰度实验。
  • Mooncake v0.3.14 的 arrays API 存在性与 vLLM connector 接入是不同层级；本次明确核对 v0.34.0 sender 和 #67656 合入代码，未声称所有更新版本都采用同一后端。
  • 截至本次查询，Mooncake #5525 仍 open；相邻 TENT 提议不是本报告 classic TE 实测收益，也不是已经发布的保证。
  • 公开作者的平均带宽/计时不能推出用户业务 p99，不能直接套到 SGLang、vLLM-Ascend、不同 KV dtype/attention 布局或不同网络。
  • 先建立产物清单、关联采样字段和可回滚试验。没有真实流量匹配验证之前，只能说“值得评估”，不能说“已适用于生产”。
推导 / 教学示例

可沉淀的工程亮点是一套“固定字节、变化形状”的 P/D 故障诊断包：一张分层面板、一个脱敏关联样本规范、一组布局/API 对照测试和一份灰度门禁。它使 SRE 能把网络问题、CPU 提交问题与容量排队分开交给对应团队，而不是把所有慢请求都归为带宽不足。
