结论：安全退出需要三种所有权一起成立

推导 / 教学示例

采用 Mooncake ProcessGroup 的服务若在通信对端退出、反复建组销组或负载退出时出现 Asio 崩溃，这项修复值得优先评估。它同时处理 socket 操作应在哪个执行器启动、异步地址字符串活多久、拥有回调对象何时可以销毁。只修其中一个维度，仍可能留下另一种退出竞态。

官方事实[2] ↗[3] ↗

最终实现把异步地址参数改为按值保存在协程帧中，并将析构连接到 shutdown；关闭会等待登记的异步任务归零，再关闭缓存客户端。

推导 / 教学示例

本报告最重要的采用建议是：把“关闭标志已置位”“本地任务和回调已排空”“对端业务已完成”拆成三个事件。补丁主要建立前两者之间的等待关系，并不增加业务级确认、持久化或 collective 成功保证。性能收益也不能由崩溃修复直接推导。

背景：缓存连接把一次请求延长为跨线程资源

推导 / 教学示例

复用客户端能避免每次 RPC 都重新建连，但也让同一个 socket 经历多个调用线程和多次对端状态变化。调用方在线程 A 取到缓存对象，不代表能在 A 上安全启动任何操作；对端关闭可能已经让 socket 的执行器 B 处理错误和清理。指针仍有效与操作可并发是两种不同保证。

作者报告结果[4] ↗

作者将原故障归因为异步缓存发送在非 socket 执行器启动，与 peer-close 竞争；同时报告了 ASan 与 TSan 复现。

推导 / 教学示例

字符串还有独立寿命：外层 API 的 const reference 在调用返回前有效，异步协程却可能稍后才开始读。协程帧保存的引用不会自动延长被引用字符串寿命。因此，地址值的拥有权需要在排队前建立，不能依赖连接缓存或者 shared_ptr 顺便解决。

推导 / 教学示例

这里的 PG 控制面 RPC 以 host 侧 C++ 协程和 socket 为核心。它不是前一篇 CUDA EFA/FI_HMEM 的设备内存注册，也不是 Ascend NPU 的 HCCL 或 MemFabric 修复。CPU 控制面测试、CUDA collective 测试和 NPU 验证必须分别记账。

原理：执行器归属、任务账本和回调退出

官方事实[2] ↗[3] ↗

getOrCreateClient 在连接前切换到客户端 executor；send 与 callAsync 在发起写入前也切换，并再检查关闭标志。同步 call 与 tryReconnect 的连接同样显式指定客户端 executor。

推导 / 教学示例

这里的“串行化”针对 socket 的操作归属，不等于整个 RPC 客户端只有一条全局串行请求队列。多个 peer 可以有各自连接，缓存慢路径仍在锁外进行握手；不能把一次 executor 跳转当成应用级互斥，或假定它能替所有上层状态加锁。

官方事实[3] ↗

spawn 在共享 mutex 下同时检查关闭标志和增加 pending_tasks。shutdown 持同一锁置位，再用条件变量等待零；等待会释放锁，完成处理器因而能取得锁并减计数。归零后交换出缓存，在锁外逐个关闭。

推导 / 教学示例

关键顺序是“停止接纳 → 等待已接纳任务 → 关闭连接”，不是先关 socket 再希望所有回调自然消失。任务的完成处理器包在协程外面，协程中已经进入的回调需要返回，任务才能退休。这让 owner 在 shutdown 返回后再销毁被回调捕获的对象有了可核对的本地顺序。

推导 / 教学示例

关闭标志读取与回调进入之间不是一个原子事务。一个已经读到未关闭状态的回调，仍可能与随后置位交错；正确验收目标应是关闭返回后不再有这些已登记任务的回调，而不是声称标志一置位就绝不再进入任何回调。此处是对原子读取与普通函数调用之间窗口的代码推导，尚未由本报告并发实验确认。

推导 / 教学示例

还有两个必须保留的边界。其一，pending_tasks 只由 spawn 路径登记，不能因此宣称同步 call 或 tryReconnect 都被统一纳入关闭账本。其二，condition_variable 的等待没有独立截止时间；请求超时设置不等于 shutdown 整体上界，用户回调或 executor 的活性仍可能影响退出。

取舍：退出变慢可能是显露真实在途工作

推导 / 教学示例

等待任务排空可能让析构延迟变长。以前仅设置标志就返回，看起来“退出快”，但不等于回调停止；修复后暴露的等待可能正是原来未被计入的资源寿命。反过来，等待本身也需要预算和可观测性，否则关闭卡住会变成新的运维盲点。

推导 / 教学示例

缓存客户端使用共享拥有权延长对象寿命，不自动保证其底层 socket API 可在任意线程并发调用。地址复制避免了引用悬空，也不代替连接成功、请求成功或业务幂等性。应分别测量它们，不把多个正确性维度合并成一个“线程安全”标签。

官方事实[2] ↗

shutdown 的接口注释明确要求由 owner 在 RPC 回调外调用；析构现在也会调用 shutdown。

推导 / 教学示例

因此，回调里销毁最后一个 owner 或直接调用 shutdown 都应视为高风险用法：当前回调所属任务尚未退休，却在等待包含自己的计数归零。这个自等待路径是代码层面的故障假设，不能作为已观测线上事故陈述。上层生命周期应把最终销毁安排到独立拥有者线程，并保持 executor 存活到关闭结束。

官方事实[9] ↗

截至本次核验，正式 Latest 为 v0.3.14，发布时间 2026-11-03；#5098 是之后的 main 修订。
