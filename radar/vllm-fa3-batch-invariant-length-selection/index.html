vLLM 批次不变性：统一 FA3 长度元数据，而不是照抄旧滑窗方案

原文 2026-11-08核对 2026-11-08

解读 #65627 最终两行修复，拆开 host 选择上限与真实 KV 长度，核对更新后的 H100 正反测试与旧 PR 描述差异。附原创机制图和验证矩阵。

一 结论：固定元数据，不是关闭滑窗

官方事实[1] ↗

vLLM #65627 于 11 月 8 日合入。最终修改是 batch-invariant 模式下令 FlashAttention builder 的 max_seq_len 等于 max_model_len，并新增定向测试；不是 PR 旧描述中的逐层 window_left+2。

推导 / 教学示例

工程判断应落在“消除一个选择输入的批次依赖”上。相同注意力掩码与数学函数，可以因为归约 tile 不同而经过不同的浮点运算路径。固定 host 选择上限有机会消除这一差异来源，但不能替代对实际 kernel、有效 KV 访问、完整输出和性能的验证。

推导 / 教学示例

建议首先确认服务确实启用批次不变性、使用 FlashAttention，并在同一配置下交替出现图回放与 eager。满足这些条件时，把此补丁纳入数值一致性候选；没有进入该路径的服务不应因标题中的“滑窗修复”而直接升级或承诺收益。

二 背景：数学等价为何仍不逐位相同

作者报告结果[4] ↗

冻结 FA3 host 代码在左窗口覆盖最长序列时可将窗口消去，同时另行接收每请求的 seqused_k。这里讨论 host 的分支输入，不是把最大长度当成每个请求的实际长度。

作者报告结果[5] ↗

冻结 tile 函数在相关 head-dim-256 非 FP8 分支给 local 路径 64、另一分支 80 的 KV tile。这个事实限定于所读函数和条件，不能外推所有 head dimension、dtype 或 FlashAttention 版本。

推导 / 教学示例

原创教学例：同一串数按不同分组求和，实数代数结果不变，但浮点舍入位置可能不同。在线 softmax 还包含分块最大值、归一化与累加状态，重排会改变中间值。若服务要求跨批次逐位相同，测试应检查 token 与 logprob，而不只检查容差内接近。

推导 / 教学示例

如果目标序列短到两个候选 tile 都只需一块，路径选择差异可能没有形成有效的多块归约见证。因此一个通过的短序列测试既可能说明修复有效，也可能说明它从未触发能够暴露问题的形状。

三 机制：选择上限与实际长度分开审查

官方事实[2] ↗

最终 builder 仍从 common metadata 获取 seq_lens、block table 和 slot mapping；变更覆盖该 builder 的 batch-invariant 分支，并非仅在 windowed layer 判断。既有分支也会禁用 AOT schedule 并固定 max_num_splits=1。

推导 / 教学示例

由此推导：模型上限若高于窗口，统一输入可能使相关 eager 和 captured 路径都保留 local 选择；模型上限不超过窗口时，两边也可能一致地消去窗口。所以准确叙述是“固定选择输入”，不能继续沿用“每一步都强制保留滑窗”的旧方案叙述。

推导 / 教学示例

该修复没有增加实际 token，也不等于分配与上限等长的新 KV。必须沿调用链核对每请求长度如何传递、后端是否仍以有效长度保护访问。将 host 启发式参数和设备端访问长度混在一起，会导致两个相反的误判：要么把合法上限误报成越界，要么在真实长度失配时误以为上限已保证安全。

推导 / 教学示例

现有并行、RSWA、encoder 或 speculative 分支不能因为共用一个 builder 就视为已验证。本次改动消除一个输入变量，不说明后续所有 branch、不同 backend 和所有随机源均已稳定。

推导 / 教学示例

证据链应保存三个独立身份：实际合入的代码、生成结果的测试版本、报告测试的运行环境。旧补丁的成功日志可以帮助定位机制，但不能自动证明后续简化版本。这里找到了针对最终 max_seq_len override 的较晚正反对照，因此不能沿用旧正文的“更新测试仍待 H100”状态；也不能把社区评论写成本站实测。

推导 / 教学示例

原始评论里大幅数值差异不应被单独当成模型质量损害的量化结论。它是一个逐位不变性反例；最终业务影响还需要真实提示分布、生成长度和下游质量评估。

五 取舍：确定性需要独立的成本账本

推导 / 教学示例

固定上限可能改变后端调度启发式在短请求上的选择，也可能影响临时内存或并行程度。即使只改 Python 整数，也不能推导设备执行成本为零。性能比较必须固定服务配置与批次分布，并同时记录实际 kernel 名称、数量及耗时。

推导 / 教学示例

不要把“保持固定选择”与“总是选择最快 kernel”绑定。线上策略可以在严格逐位不变性与吞吐目标之间做明示选择，但不能一面宣称逐位合同，一面让负载组成静默改变计算路径。若业务只要求数值容差，应以实际需求作决策，不能把更严格合同的成本隐藏起来。

推导 / 教学示例

本主题不是禁用滑窗，也不是扩大每条序列的注意力可见范围。对非滑窗层与其他模型的影响属于需要测量的范围，而不是正文旧句“其他配置完全不变”能够覆盖的结论。

九 版本与未验证边界

官方事实[10] ↗

直接读取 v0.33.0 标签 backend，目标 builder 尚无本次 max_seq_len=max_model_len 赋值。该结论只覆盖所读标签文件，不代表任意厂商 wheel 或回移补丁。

推导 / 教学示例

发布身份至少有源码提交、源码标签和安装制品三层。标签名称不能证明目标 wheel 包含补丁，某个标签存在也不等于已完成正式 Release 发布核验。本报告以固定提交为修复身份。

待验证

未验证发布制品的包含关系、完整 GPU/服务回归、跨架构成本与其他 backend 的确定性。CPU 枚举与 schema 通过仅证明教学模型及交付格式，硬件验证仍未执行。
