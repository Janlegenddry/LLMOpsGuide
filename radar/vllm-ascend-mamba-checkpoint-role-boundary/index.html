Ascend Mamba 缓存边界修复：写入策略必须与实例角色一致

推导 / 教学示例

这项改动适合正在排查 Ascend 混合模型“重复输入却不命中缓存”的运维人员。关键检查不是缓存开关是否打开，而是 prefill 如何分块、Mamba 状态存到哪个 token 边界、再次查找时各缓存组接受哪个边界。这三者不一致，增加缓存空间也不能产生本来应当存在的共同命中。

官方事实[1] ↗[2] ↗

#21063 在 main 增加角色 gate：只有启用 EAGLE、角色不跳过 drop、且属于被标记的 Mamba 组时，才设置 checkpoint-drop。组选择不变。

推导 / 教学示例

部署判断应拆成三步：先确认运行产物包含改动，再证明各组边界一致，最后验证模型输出及 P/D 传输。缓存命中恢复不代表传输映射、并发和服务 SLO 已经恢复。本文只讨论 Ascend NPU 路径，不把作者 A3 结果转述为 H20 或 GPU 结论。

背景：Mamba 状态不是可任意截断的 KV 前缀

推导 / 教学示例

全注意力 KV 可以理解为沿 token 位置积累的历史；Mamba checkpoint 则承诺“这份状态对应某个精确前缀”。对于混合模型，前者找到了更长前缀并不够，后者也必须拥有可以从同一边界恢复的状态。运维指标若只有一个总命中率，很容易把状态位置错误误诊成缓存容量不足。

官方事实[2] ↗

冻结协调器将各类型的候选命中反复收敛到共同长度；纯 P 和独立实例已有跳过 EAGLE drop 的策略，consumer 与 kv_both 保留该保护。

推导 / 教学示例

读路径已有角色判断，并不自动让写路径一致。另一处初始化若只看到“正在使用投机解码”，就可能仍然让 Mamba 写入少保留一块。修复的教学价值在于：角色策略应成为跨读写两端的同一契约，而不是两段看起来相似却分别维护的条件。这里的 drop 是可复用 checkpoint 边界计算，不是将所有物理状态页立即释放。

原理：把写入边界和查找边界放到同一坐标系

官方事实[3] ↗

上游边界函数在不 drop 时先预留至少一个重算 token，再向 hash 粒度下取整；drop 时先按输入对齐，再减一个粒度，最终截到非负。

推导 / 教学示例

取一个原创标量例子：输入 N=513、对齐 H=16、hash lookahead=0。不 drop 的边界为 floor((513−1)/16)×16=512；drop 的边界为 floor(513/16)×16−16=496。这里的 16 是边界计算粒度，不等于 Mamba 物理页大小，也不等于每次传输的字节长度。

官方事实[4] ↗[1] ↗

MambaManager 用该开关计算预留 checkpoint 位置，也在 partial-tail 的 hash 登记和保留判断中读取它。修复没有修改模型 forward 或该边界函数。

推导 / 教学示例

不要为了追求命中率，把 consumer 和 kv_both 的 drop 也一并关闭。它们需要处理外部加载和验证窗口，这与只有本地已验证 prompt 的场景不同。现场应记录角色布尔值、Mamba 组 marker、use_eagle 和最终 manager flag，而不是仅凭启动命令的名称判断执行分支。

取舍：命中资格恢复不是普遍性能提升

推导 / 教学示例

最相关的负载是使用细粒度前缀复用、Mamba align 和投机配置的 Ascend 混合模型，尤其输入长度刚越过某个 hash 边界的重复请求。全冷请求、未标记的 Mamba 组或关闭投机的负载未必经过该条件。即便命中 token 变多，也要看省下的 prefill 是否抵消查找、恢复和通信开销。

官方事实[8] ↗

正式版列表当前标记 v0.30.0 为 Latest；本次主分支改动不因此成为正式发布内容。

推导 / 教学示例

还要区分三个尺度：hash/PMU 决定候选边界，物理页决定存储布局，传输层按自身步长搬运。它们需要相容而非数值相等，不应为了追求更长命中而绕过配置约束。

作者报告结果[6] ↗

作者的 PMU 512 在补丁前后都被 1152-token 物理页整除检查拒绝。
