Ascend 显式选卡与 KV 分片：设备号不能代替 worker rank

原文 2026-11-09核对 2026-11-10

解读 11 月 9 日合入的 #19826：SFA sender 沿用 worker 已选 NPU，非复制 native tiering 按逻辑 rank 分槽。解释为什么 HTTP 与 H2D 哈希都成功，仍可能读回已被覆盖的 KV；附版本边界、源码证据、机制图和待执行验收矩阵。

结论：分别证明设备绑定和 KV 槽归属

推导 / 教学示例

使用非连续或重排设备 ID 时，服务成功响应不能代替 KV 正确性验收。本次最值得检查的是两个不同身份：发送线程要沿用所属 worker 已选中的 NPU；非复制 CPU tier 的字节槽要按照 worker 的逻辑 rank 分配。设备编号决定在哪里执行，逻辑 rank 决定哪一份分片归谁，不能互相替代。

官方事实[1] ↗[2] ↗[3] ↗[4] ↗

#19826 于 2026-11-09 合入 main，固定提交 f622e04c602e。改动把 SFA sender 的设备来源从 local_rank 改为 producer 捕获的 current_device，并把非复制 native tiering 的槽号从 device % world_size 改为 config.parallel.rank。复制布局仍取槽 0。

发布边界

官方事实[11] ↗[12] ↗[13] ↗

本次确认的是 main 源码修复，不是一个新正式版本已可安全升级。核验时公开最新正式版本为 2026-10-29 的 v0.30.0；该标签固定提交的两处代码仍是旧算法。实际镜像是否包含回补、具体模型是否进入这两条路径，都必须按产物核对。

推导 / 教学示例

建议优先排查“显式选卡 + SFA PD”以及“显式选卡 + 非复制 native tiering”两类部署。先做身份与字节证据，再做端到端质量和延迟测试；不要因 HTTP、传输返回码或最终答案看似正常就结束验证。

背景：同一个数字可能属于不同编号空间

官方事实[2] ↗[3] ↗[13] ↗

SFA producer 在注册 KV 后创建发送线程。修复前，线程直接把本进程的 local_rank 解释为 NPU 编号；修复后，producer 在线程创建前读取当前设备并显式传给线程，线程再绑定该值。因而选择设备的决定只在 worker 一侧作出，辅助线程不重新猜测。

官方事实[4] ↗[5] ↗[6] ↗

native tiering 的另一条链路面向共享 CPU mmap。vLLM 为同一 engine 的 chunk 行定义固定字节跨度，每个 worker 在每行的起始偏移由 rank × cpu_page_size 决定；调度器视图使用 rank=None，覆盖完整区域。Ascend 新实现与上游 worker 的 rank 规则保持一致。

推导 / 教学示例

两个错误可以独立存在。线程选错 NPU 不等于 CPU 槽一定碰撞；CPU 槽碰撞也不要求发送线程参与。生产诊断必须分别记录进程内设备 ID、逻辑 rank、engine 身份与 mmap 区间。容器可见设备映射还可能改变编号含义，因此不要仅凭主机物理卡号推断 torch.npu.current_device() 的返回值。

作者报告结果[10] ↗

作者在 Atlas 900 A3 上报告：Qwen3-8B 的 TP2 native tiering 使用设备 1、3 时，旧路径和新路径均得到 12/12 HTTP 200，旧路径却有 5 次 D2H 哈希不符；新路径报告 22 次 DMA 哈希全部一致。此处仅转述作者结果，未独立复现。

机制：两条身份链各自闭合

推导 / 教学示例

把 W 记为该配置的 world_size，d 为进程内选中的设备号，r 为 worker 逻辑 rank。旧非复制槽号 d % W 只有在设备列表与逻辑分片顺序恰好一致时才成立。设备 1、3 且 W=2 时，两者余数均为 1，两个不同分片会指向同一段 CPU 字节。设备重排还可能产生另一种更隐蔽的失败：槽号不重叠，却与调度器期待的分片顺序交换。

相同共享文件不意味着所有 worker 可以写同一片字节。SharedOffloadRegion 的行内偏移和边界检查只能验证一个槽内部没有越界；若两个调用者提交了相同但错误的槽号，它们各自都可能通过局部边界检查。此时需要跨 worker 比较身份和区间，而不只是逐进程检查地址合法。

启动信号不是成功信号

官方事实[2] ↗[3] ↗[13] ↗

冻结 sender 在设备绑定失败时保存 startup_error、设置 ready_event 并退出；producer 等到事件后仍会检查 startup_error 并抛出启动异常。这些错误处理在相邻旧代码中已经存在，本次关键变更是传入正确设备身份，不能把整套启动错误传播都写成 #19826 新增。

边界：有意共享不应被修成一律分离

官方事实[4] ↗[7] ↗

修复没有把所有布局都拆成独立槽。NPUTieringOffloadingSpec 对被判定为复制布局的情况继续使用 rank 0；普通 NPUOffloadingSpec 则维持 pinned tensor 的单 CPU tier 路径。本次结论针对共享 tiering 的非复制槽算法，不能推导“所有相同槽号都是错误”。

推导 / 教学示例

有意复制共享需要的是相同字节语义；意外碰撞则是把不同 rank 的分片混在一起。验收时应先记录 replicated_layout 的实际值和产生依据，再选择“应相同”还是“应互不覆盖”的断言，否则容易把合法去重当成回归，或以复制为借口掩盖非复制碰撞。

作者报告结果[10] ↗

SFA 作者测试采用 GLM-5 W4A8 与 MemFabric SDMA 1.2.1，修复前后答案与传输读取均成功，差异由 sender 与 worker 设备一致性观察揭示。作者明确没有给出性能基准，也未覆盖 DeepSeek-V4.1-Flash 与 Atlas 850E。

推导 / 教学示例

因此不能把该修复外推为 H20/SGLang 性能提升，也不能凭 A3 结果推荐所有 Ascend 卡型升级。对于默认连续同序编号的部署，两种算法可能给出同样结果，基线正常不代表非默认选卡安全。更合理的取舍是优先给实际使用显式选卡和多级缓存的组合补验收，而不是为全部工作负载声称同一收益。

生产诊断：哈希相同也可能读回了错误历史

推导 / 教学示例

最危险的误判是只检查一次搬运的起点和终点。若 worker B 先覆盖了 worker A 的 CPU 槽，随后 H2D 复制可以忠实搬走这份错误内容，于是 H2D 前后哈希相同。正确诊断要同时保存 offload 时该逻辑 chunk 的参考摘要、CPU 驻留期间的摘要、reload 来源和回到 NPU 后的摘要，并带上 engine、rank、chunk 身份与本次分配代次。
