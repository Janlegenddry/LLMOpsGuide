从运维走向 AI Infra，关键是把负载与 SLO 翻译成系统选择：延迟、吞吐、容量是不同约束，先拆请求路径，再解释瓶颈。

证据与判断

已确认事实

原文按负载、上下文长度和 SLO 选择 prefill 与 decode 的服务配置。MoE EP 的 rank 偏斜可能使通信量较少的路径反而更慢，适用边界是文中评测负载。

证据 1 ↗

已确认事实

271 tok/s 是 batch=1、单节点 8×H20-141GB、TP8 的参考结果。作者从服务端 Decode batch 日志去掉最高和最低各 20% 样本后取均值；它不是客户端端到端吞吐。

证据 1 ↗

推测

迁移到自己的服务时，可先定位排队、prefill、KV 传输、decode 各阶段的等待与执行，再决定优先调哪个资源。多个环节重叠时，不能把所有 span 的时长简单相加。

待验证

投机收益应按每个有效输出 token 的总成本验证，草稿、验证、调度和通信开销都要计入；只看接受率不足以决定上线。

教学例子 · 非实测

同一个“首 token 变慢”现象可能有不同原因：如果计算 span 不变但队列增长，优先验证准入和负载；如果队列稳定而某个 rank 的 prefill 延长，优先验证路由偏斜。先写可证伪假设，再用同一请求的 trace 和 rank 指标逐个排除。这个例子不代表任何真实线上故障。

带回实践的验证问题

  1. TTFT 上升时，是排队更长、prefill 更慢，还是 KV 传输等待？
  2. 各 rank 的耗时和 expert 路由分布是否揭示最慢 rank？
  3. 关闭/开启投机，在相同负载与 SLO 下，每 GPU 秒的有效输出 token 是否增加？

这些是实验问题，尚未作为本站的实测结论。
