结论：把优化文章读成因果链

推导 / 教学示例

读优化文章最重要的，是建立“业务负载和 SLO → 瓶颈 → 并行拓扑 → 执行优化 → 验证结果”的因果链。单请求生成快、单位 GPU 产出高、长上下文装得下，是三种不同目标；在一种考试里拿到最佳成绩，并不自动通过另外两种验收。

作者报告结果[1] ↗

原文的 271 tok/s 是一个明确配置和统计口径下的作者结果，不能直接承诺客户端端到端吞吐或 p99。采购和部署选择应固定请求分布、质量门槛、总 GPU 数及整条服务链成本，再比较可交付能力。

推导 / 教学示例

从运维走向 AI Infra，要先解释请求在哪里等待、状态放在哪里、最慢路径为何变长，再决定调缓存、并行拓扑还是投机预算。证明优化帮到了自己的负载，比复述一个速度数字更有用。

先确认成绩属于哪场考试

作者报告结果[1] ↗

271 tok/s 来自 8×H20-141GB、单节点 TP8、batch=1、256K 输入的参考配置。作者从服务端 TP0 的 Decode batch 日志剔除最高和最低各 20% 样本后取平均。它不是客户端端到端吞吐，也不是客户端 p99。文中不同最佳成绩对应不同服务配置；B300 是外部参考，不能作为严格同条件对照。

推导 / 教学示例

先在实验记录里写清“谁计时、从哪里开始、在哪里结束、失败样本如何处理”。否则服务端 decode 步时、客户端流式间隔、整条服务链吞吐会被放进同一张比较表，结论就失去可解释性。

三个目标，三套验收

推导 / 教学示例

延迟：代表性请求能否在预定时间内交付？吞吐：所有 P/D/草稿资源投入后，每秒有多少合格请求完成？容量：在实际 KV 布局与安全余量下，能否准入足够长的上下文和并发？不要用其中一个指标替代另外两个。

请求、通信、KV 与投机的因果链

官方事实[2] ↗

SGLang 的 P/D 分离把输入计算和逐 token 生成放在不同实例，减少 prefill 对 decode 的干扰，并以 KV 传输衔接两侧。拆实例能隔开执行阶段，也会增加交接、分配及失败恢复的边界。

推导 / 教学示例

TP 拆张量，PP 拆层，CP 拆上下文，EP 拆专家；Attention-DP 分配请求的注意力工作，不等于复制所有专家。拓扑决定状态放置和跨卡、跨机的数据流。看 TTFT 超标时，要区分排队、输入计算和 KV 交接；看生成卡顿时，要区分 attention、MoE、通信和调度空隙；请求进不去时，要区分内存不足、准入约束和计算饱和。

MoE：传得少，为何仍然慢？

官方事实[3] ↗

MoE 的执行涉及 token 分发、布局变换、专家计算和结果回收。EPLB 根据激活统计调整专家的放置或复制；这种调整针对负载分布，不能只凭传输总字节判断效果。

推导 / 教学示例

在上面的非实测算例中，A 的同步关键路径约为 max(2,2,2,10)+2=12 ms，而不是 rank 平均计算时间加通信。B 虽然通信更贵，总路径约为 max(4,4,4,4)+4=8 ms。说明更少通信量可能被更严重的计算偏斜抵消；实际有重叠时，仍应以时间线找关键路径。

官方事实[4] ↗

AllGather 汇集各 rank 的数据，ReduceScatter 先归约再分片，AllReduce 使各 rank 得到完整归约结果。collective 等待长，也可能是其他 rank 的计算尚未完成，不能直接归因网络。

推导 / 教学示例

KV 可用空间 = 设备内存 − 权重 − 运行时缓冲 − 通信 / 图捕获 / 草稿状态 − 安全余量。假设某个 rank 剩 96 GiB，真实布局每 token 消耗 512 KiB，理论池为 196608 token。每请求预算 48K 输入加 8K 输出（这里 K=1024），只能容纳 3 个完整请求，且尚未计分页取整。这不是 DeepSeek-V4 的 KV 估算。压缩注意力、层结构、分片与辅助状态会改变每 token 成本，应以真实分配器核算。

投机：算实际提交 token 的完整成本

推导 / 教学示例

每个有效输出 token 的成本，应以完整迭代墙钟时间除以实际提交 token 数。有执行重叠时取关键路径，不机械相加 kernel 时长。原创例子：普通解码 12 ms/token；A 每轮 18 ms 交付 3 token，成本为 6 ms/token；B 每轮交付 4 token，但耗时 28 ms，成本为 7 ms/token。B 接受更多，单位输出却更贵；以上不是实测。

官方事实[6] ↗

DSpark 使用分块草稿与置信度驱动的可变验证调度。是否真的减少成本，还要看验证执行路径、草稿、同步和状态开销；不能为提高接受率擅自改变采样或接受规则。

官方事实[7] ↗

指标源码中的 spec_accept_length 包含接受草稿和 bonus，而 spec_accept_rate 是接受草稿数除以提出草稿数，两者分母不同。比较时还应同时看完整迭代墙钟、KV 占用和质量，避免只用一个接受率解释收益。

取舍：容量、延迟与吞吐不能互相代替

官方事实[5] ↗

Humming 集成包含 Hopper W4A8。

推导 / 教学示例

低比特释放权重空间，并不自动证明执行更快。它可能首先允许更多并发，而更高并发又会增加访存、通信与等待。最终应比较 SLO 达标后的吞吐；权重占用下降只是容量链上的一个环节。

推导 / 教学示例

P/D 分离减少输入计算对生成的干扰，却引入 KV 交接；更宽 EP 可能减轻单 rank 专家负载，也改变通信与偏斜；投机可能减少目标模型轮数，也增加草稿与验证状态。这些方案应按同一请求分布评估，不能把不同 A/B 的收益百分比相加。

推导 / 教学示例

某方案只改善平均延迟却恶化长尾时，可以限定到特定低并发或短输入负载，不应直接成为全量默认。质量、稳定性和状态正确性始终先于资源效率。

生产故障关联：拆开握手、分配与搬运

官方事实[2] ↗[7] ↗

指标源码区分 bootstrap 时间、KV 分配等待、传输延迟与失败计数。PD 文档提醒，提高 bootstrap timeout 会延后 D 失联时 P 侧相关内存清理。延长超时可能只是让故障更晚暴露。

指标与验收：统一客户端和服务端口径

官方事实[8] ↗

TTFT 是到首 token 的延迟，ITL 是客户端观察到的 token 间隔；逐请求 TPOT =（总延迟 − TTFT）/（输出 token 数 − 1）。不足两个输出 token 的请求应单独处理。

推导 / 教学示例

保留客户端 TTFT、TPOT、ITL 的分布和样本数。一次流式发送可能包含多个 token，客户端 ITL 会受缓冲影响；p99 需要足量请求与持续负载，不能从均值推断。成功输出 tokens/s 应注明失败和重试如何计入。

验收表：门槛在实验前约定
维度统一口径验收要求依据
质量 / 正确性同模型、采样和请求集；记录任务分数或数值误差。先通过预定质量门槛，不能为速度改掉比较条件。待验证
延迟客户端 TTFT / TPOT / ITL 分布、样本数与负载持续时间。分别满足预先约定的 SLO；不足两 token 的 TPOT 单列。待验证

稳定性失败、重试、取消后回收、故障恢复边界。质量和隔离稳定后再选择成本最优配置。待验证

证据 1 ↗

推测

迁移到自己的服务时，可先定位排队、prefill、KV 传输、decode 各阶段的等待与执行，再决定优先调哪个资源。多个环节重叠时，不能把所有 span 的时长简单相加。

待验证

投机收益应按每个有效输出 token 的总成本验证，草稿、验证、调度和通信开销都要计入；只看接受率不足以决定上线。

  1. TTFT 上升时，是排队更长、prefill 更慢，还是 KV 传输等待？
  2. 各 rank 的耗时和 expert 路由分布是否揭示最慢 rank？
  3. 关闭/开启投机，在相同负载与 SLO 下，每 GPU 秒的有效输出 token 是否增加？
