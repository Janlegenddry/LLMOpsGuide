先把失败限制在请求，再讨论恢复吞吐

官方事实[1] ↗

SGLang #43562 创建于 10 月 10 日 13:50:46 UTC，10 月 11 日 02:12:35 UTC 合入 main，合并提交为 e1f43c9a61db335f99f47c981222170cbf9c82ab。它属于本轮时间窗的新变化。

推导 / 教学示例

对开启 PD、decode 侧 radix cache 与 HiCache、且 decode 使用 attention TP 的团队，这比一般速度优化更值得优先做故障演练：一个 rank 的局部恢复失败，不应把其他请求拖成进程级故障。判断修复是否有效，需要同时看请求终态、各 rank 队列身份和可用预算；只看到一次 all-reduce 返回相同值，证据还不够。

待验证

不建议凭本文直接升级生产。首先核对实际镜像是否包含该提交；然后在与生产相同的后端、TP 拓扑和缓存压力下验证。没有开启上述组合的服务，可列为升级检查项，无需因这条消息改动现网。

一个请求同时欠两笔账

推导 / 教学示例

PD 的 decode 端并不一定从 prefill 端接收完整上下文：它可能已有本地前缀，其中一部分又只留在主机缓存。因此一个请求可能同时等待“P 发来的数据”和“D 从主机恢复的数据”。两条路径的完成时刻不同，出错方式也不同。数据传输结束，不自动意味着请求已能交给模型计算。

作者报告结果[10] ↗

PR 作者报告：在 Qwen3-0.6B、P TP1 / D TP2、NIXL、decode HiCache 的故障注入中，单 rank 的 load_back 返回失败能使旧路径的后续 Gloo 集合通信崩溃；修订路径中路由重试后该轮及后续轮请求完成。所述是作者实验，未给出 H20 适用性证明，也不能把路由重试成功解释成第一次尝试成功。

官方事实[6] ↗

另一个相关修复 #41393 已于 10 月 1 日合入，它处理局部 load-back 事件驱动集合通信的问题。它是本次研究的背景，不能重新包装为今日新消息。

推导 / 教学示例

两类问题外观相似，却处于不同边界：前者是哪些 rank 进入集合通信；本轮关注进入后怎样共同决定请求去留。诊断时应寻找第一次分叉，而非把最后一条 Gloo 长度报错当作根因。

状态归约和资源预留是两道独立约束

官方事实[2] ↗[3] ↗[4] ↗[5] ↗

固定源码中，KVPoll 由 Failed=0 至 Success=4 排列，投票使用 MIN。HiCache gate 只在传输已 Success 时将本地 PENDING 降为 Transferring、FAILED 转为 Failed；非终态传输保持原状态。staging 路径也接收这些 gate。请求处理依据归约结果作分支。

推导 / 教学示例

这项归约按数组槽位配对；只有各 rank 对应槽位代表相同请求、顺序一致时，才能把相同归约值解释为同一请求的共同结算。MIN 本身不是队列身份共识协议。任何“同一轮”或“共同退休”的推断都以这一前提成立为条件，仍需逐 tick 的有序请求标识证据。

推导 / 教学示例

原创教学示例：rank A 已为一次恢复占用 3,000 token 的设备空间，rank B 分配失败，因此 B 的原始可用量比 A 多 3,000。若 B 立刻把这次请求从预留中删除，B 可能多准入一个新请求。旧请求的失败状态即便已准备传播，新请求也会把两边队列重新拉开。这里的关键不是把所有 rank 的物理内存强行变成一样，而是在同一轮 admission 判断中，不提前花掉尚未共同结算的额度。

官方事实[2] ↗[5] ↗

修订后的预留计算覆盖 transfer queue 中有 prefix match、但没有 restore lock 的请求，不再只计 PENDING；admission 从 full token budget 中扣除这个预留。未获锁的 FAILED 请求因而不会仅凭局部状态提前释放预算。

推导 / 教学示例

数字示例：A 原始余量 5,000，B 原始余量 8,000；B 继续扣除 3,000 待结算额度后，两边均以 5,000 作本例中的准入判断。该数字不是显存测量，实际分配器还有其他扣减项。

推导 / 教学示例

下面用两幅原创机制图分别呈现状态边界与预算账本，避免把两者误读成同一条时间线。

推导 / 教学示例

图 A：两 rank 的状态边界。节点为 A 的 transport success / restore ready，B 的 transport success / restore failed，分别进入各自 gate，再汇入 existing MIN poll，最后到“在各rank投票数组请求身份与顺序一致的前提下，共同拒绝该请求”。在独立旁路画“transport 未终态 + restore failed → 保留在途”，这里不存在直接释放页的安全推论。图示边界：这是两 rank 的 transport 均已 Success、且投票数组请求身份与顺序已一致的教学场景，非实测；MIN仅保证对应槽位值一致，不自行证明队列身份或顺序。MIN 一致失败只说明控制结果一致，不能证明所有远端 DMA 已停止。若 A 已 Success 而 B 仍 Transferring，A 的 Failed 仍可经 MIN 传播，必须另验归约后的清理和远端写停止边界。独立旁路仅表示本 rank 的未终态 transport 不被本地 restore failure 改写，不代表跨 rank 安全栅栏。

推导 / 教学示例

图 B：预算双账本。A 的“真实已分配”与 B 的“失败但仍保留预留”并排，各自扣减原始 budget，再进入“本轮可准入额度”；独立节点写“共同移出队列后再结算”。箭头标明扣减关系，不将 5,000 / 8,000 画成实测比例或等待耗时。

保留额度会暂时少接单，但不能省略

推导 / 教学示例

失败尚未共同退休时，保留额度可能暂时压低 admission。它是一种安全约束，不能只按即时显存利用率评判。如果请求迟迟不能进入终态，这笔额度也可能长期挂账。因此验收须同时规定安全性与有界进展：不能提前复用，也不能无限期扣留。

推导 / 教学示例

更激进的方案是在本地失败时立即取消其他 rank 或远端传输，但它需要证明取消传播、远端写停止和资源释放之间的先后关系。本文不把这种想法当作现有实现。另一个方案是额外集合通信协商状态，代价是增加控制路径与配对复杂性。本次应先评估已有归约路径能否完整覆盖需要的状态，不凭空增加通信。

推导 / 教学示例

还有一条不能省略的边界：本地 gate 不改写本 rank 的非终态传输，并不单独证明另一个 rank 报 Failed 时所有远端写都已经结束。MIN 会传播其他 rank 的失败。计划在 E3 中专门制造 A 已成功、B 仍传输的时序，核对归约后的清理约束；若缺少连接器契约或运行证据，就保留这一未知。

待验证

H20 是计划验证目标，而不是作者测试平台结论。Ascend 910 的连接器、运行时和设备同步语义另行验证，不能把这条 SGLang 修复转写成 Ascend 修复。不同 staging、host receive、CP、hybrid cache 组合均不能自动继承本文的验证结论。

三种原创故障假设与诊断证据

推导 / 教学示例

假设一：本地恢复失败首先打破 queue 身份一致性。逐 tick 记录 request ID 序列、原始 transport poll、restore 状态、gate poll、归约结果、commit/abort 决策；记录 ID 的有序摘要，而不仅队列长度。等长不同请求仍会让按位置的投票失去意义。

推导 / 教学示例

假设二：状态处理一致，但准入预算先分叉。记录每 rank 的原始 token budget、restore reservation、restore lock 是否取得、本轮新入队 ID。若失败 rank 的有效预算突然多出一个 restore_token_count，并在共同退休前多接单，证据指向账本时序；不能只看最终 OOM。

推导 / 教学示例

假设三：修复后不崩溃，却以长时间等待换来表面稳定。标记首次本地失败、最后远端写入、公共终态、最终 release 与下一请求完成的时间。若预留一直不归零而队列无进展，应检查传输终态、超时与清理，而非误判为修复“稳住了”。

待验证

上述 trace 属于拟议实验观测点，不保证现成 metrics 已提供。采用限流采样和匿名测试请求，评估插桩本身对调度时序的扰动。不要在生产随机注入故障。

消融实验的价值是防止“一个修复同时改多处，因此任一处都可单独摘取”的误判。若只保留状态修改的分支仍在 admission 边界失败，就能说明为什么预算是必要条件。实验必须以最先破坏的不变量归因，不能仅统计最终进程是否存活。
