FlashInfer 常驻累加区：流身份、负零与复用完成门

原文 2026-11-07核对 2026-11-08

一 结论：零常驻优化仍需要身份、顺序与位语义

官方事实[1] ↗

FlashInfer #9110 于 11 月 7 日合入，修改 AlphaMoE NVFP4 aligned 入口的 accumulator 缓存策略、drain 复位及重叠检查，另增回归。目标是前置优化的正确性加固，不是新的全模型加速结论。

推导 / 教学示例

采用常驻 scratch buffer 的关键问题不是“能否省一次清零”，而是下一次使用时谁能证明它仍属于同一个有序执行域、上次写入已结束、每个未覆盖位置都保持约定值。缓存 key、host 锁、GPU stream 顺序与浮点零符号分别回答不同问题，不能相互替代。

推导 / 教学示例

建议只对实际命中该 aligned NVFP4 分支的服务评估修复；将普通流缓存、图捕获、大对象和 PTDS 分开验收。尤其不能把“特殊流不留全局缓存”解释为“PTDS 多线程 allocator 问题完全解决”。

二 背景：省去初始化后，状态责任转移到收尾

作者报告结果[8] ↗

前置 #9080 将相关 aligned 入口改为先把路由贡献写入 FP32 累加区，再由 drain 加上调用方原有输出并转 BF16，随后恢复累加区静止值，以减少缓存命中时的初始化。

推导 / 教学示例

这是一种状态化优化：缓冲区不再只是一次调用的临时结果，而是下次调用的前置条件。前一次收尾缺失、调用异常、输出别名、错误的并发归类，都可能让后一次在看似合法的 shape 上读取脏状态。性能优势来自跨调用重用，因此验证也必须跨调用，单次结果正确不足以覆盖。

推导 / 教学示例

“零”至少有数值为零与位模式为某种零两种合同。计数非零元素只能检查前者，无法检测 +0 与 -0 的差别。若外部承诺未命中的输出位保持不变，就需要按位测试零符号，也要明确 NaN payload 不在同一保证内。

三 机制：同流顺序不能由 host 锁替代

官方事实[2] ↗

固定入口将大于 2²² 元素、PTDS handle=2 或图捕获中的调用转为 -0 填充临时区；普通缓存每设备最多保留 32 个流，命中更新 LRU。锁覆盖取缓存与两个 launch，异常会移除该 key。

作者报告结果[9] ↗

CUDA 文档将 cudaStreamPerThread 定义为线程相关的默认流。因此同一个特殊句柄数值不具有普通显式流那样的全局队列身份；需要区分句柄名称与其解析出来的执行队列。

推导 / 教学示例

原创推导：host 线程 A 先提交、线程 B 后提交，仅建立 host 程序顺序，不自动建立两个不同设备队列的完成先后。锁能防止共享字典被同时修改，也能让同一个普通流上的两次提交不被其他调用插入，却不能等待另一个 stream 的 kernel 完成。

官方事实[3] ↗

drain 读取 FP32 累加结果与原 BF16 输出，以 round-to-nearest 的 FP32 加法再转 BF16，并把累加区写回 -0；其入口对非空向量检查 accumulator/out 不重叠。

推导 / 教学示例

在约定的舍入规则下，-0 加 -0 保留负号，+0 加 -0 可以得到 +0。这个很小的例子说明“不贡献任何路由”的位置仍可能被一次看似无害的加法改写位模式。把静止值改为 -0 是特定算术合同的修复，不应说负零在所有运算、舍入模式和 NaN 情况下都是万能恒等元。

推导 / 教学示例

评估一个缓存修复时，至少需要“错误归类可以构造”“修订消除该归类”“实际 allocator 不早复用”“输出语义仍满足”“性能成本可接受”五类证据。测试数变多或作者运行通过不能将这些层次合并。尤其是检查缓存条目不存在，仅说明全局字典不再持有对象，并不说明设备侧寿命已正确结束。

推导 / 教学示例

性能表的采样单位是 MoE 调用内 kernel 时间总和，经多轮、重复和多 GPU 聚合；它不是端到端请求时延。报告只保留其量级与作者归因，不把接近 1 的比值包装成加速。

五 取舍：有界条目不等于进程显存有界

作者报告结果[7] ↗

作者说明缓存上限为每设备 32 个流；超过 32 个流轮转会反复付出 -0 fill 的代价。锁在完整 host 调用期间保持，保护 LRU、两个 launch 及异常清理。

推导 / 教学示例

按 32 个缓存项、每项至多 2²² 个 FP32 元素推导，单设备被此缓存显式引用的最大容量为 512 MiB。这个算术上界不包含 per-call 临时区、图内存池、分配器 reserved 内存、调用方张量及同时在途的旧对象，所以不能将其当成进程 GPU 峰值上限。

推导 / 教学示例

LRU 驱逐只是移除缓存引用，不表示 GPU 已执行完最后一次 drain，也不保证 reserved memory 立即下降。应分开记录 live cached、allocated、reserved 和图池内存。用 nvidia-smi 的一个总值判断 LRU 是否有效，可能把合理的分配器保留误报成泄漏，也可能漏掉真实的在途增长。

推导 / 教学示例

在高流 churn 或频繁图重捕获工作负载中，优化的 amortization 可能消失。合理决策应根据真实命中率、对象大小、流优先级分布与并发度，而不是把固定 32 当成适合所有部署的自然常数。

六 故障假设：缓存 key 只是第一道门

官方事实[2] ↗

源码还明确提示：PyTorch allocator 以 stream handle 归类，对 PTDS 并发宿主线程并不提供完全隔离。per-call 分支移除了此入口的全局缓存共享，却没有宣称修复通用临时张量的 allocator 风险。
