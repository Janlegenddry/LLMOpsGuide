一 结论

官方事实[1] ↗[26] ↗[27] ↗[18] ↗

vLLM #59504 于 2026 年 10 月 3 日 06:26:13 UTC 合入 main，修复异步 KV 加载与新块清零之间的竞态。[1] 截至 2026-10-08，最新正式版本为 v0.31.0，但固定标签仍未包含 #59504 的异步清零修复，也没有 #59197 的窗口加载判定接口。合入 main、进入稳定标签和进入具体 wheel/镜像是三个不同节点；部署前仍需固定双端产物并核对包含关系。

推导 / 教学示例

最重要的工程变化，是把“哪些物理块不能清零”的判断交回分配器：连接器声明本次请求恢复哪些缓存组，分配器据此处理实际分配的新块。逻辑 token 区间不足以代替这个判断。

推导 / 教学示例

对生产团队，合理的下一步是确认自身是否存在相关执行路径，再做隔离回归。不要把合入状态当作整套 P/D 正确性已获验证，也不要仅凭模型输出看起来正常就关闭问题。本文没有执行 GPU 实验；后文测试与验收均为建议方案。

二 背景

推导 / 教学示例

P/D 分离让 prefill 负责提示词计算，decode 接收 KV 后继续生成。异步加载允许传输与其他工作重叠，但同一块内存的初始化、远端写入和模型读取必须有一致的顺序。

推导 / 教学示例

理解本次问题需要区分三层对象：

推导 / 教学示例
  • 请求的 token 范围：描述序列中哪些位置已有计算结果。
  • KV cache group：一组具有共同缓存规格和管理方式的层；不同组的可缓存性、窗口和布局不一定相同。
  • 物理块：本次分配得到的存储单元；它是否需要初始化，取决于谁将写入它，而非仅看对应 token 的位置。
官方事实[3] ↗

调度器先查询本地前缀，再向连接器查询外部命中；外部命中数量和是否异步加载是不同信息。合入后的调度路径只在异步加载时传递清零豁免组，同步路径仍使用空豁免集合。[3]

推导 / 教学示例

因此，“请求命中了前五块”不能直接解释为“每个缓存组都已经有前五块可用”。把请求级命中长度投影到所有组，恰好会遮住混合缓存布局的差异。

三 机制

旧判断为什么会漏块

官方事实[4] ↗[16] ↗

旧实现根据待加载 token 区间切取各组的块列表，再从清零集合中排除这些块。问题不是区间算得不够精确，而是某些组根本不遵循这种位置映射：窗口组可能在本地命中边界之前分配新块；环形缓冲区则把自己的存储保留在块列表索引零。[4][16]

推导 / 教学示例

以下是教学例子，不是上游实测参数：同一请求的全注意力组复用了旧块 A、B，窗口组却新领到 X。X 在逻辑命中边界之前，但仍是本次传输的目标。如果区间筛选漏掉 X，分配器登记的清零任务便可能与连接器写入同时作用于 X。

推导 / 教学示例

竞争没有唯一时序。传输先写、清零后到，可能擦掉有效值；二者交叠，结果可能取决于执行顺序。传输成功只能说明连接器完成了自己的工作，不能证明另一条执行路径没有覆盖它。

新判断把职责分开

官方事实[5] ↗[6] ↗[7] ↗[8] ↗

连接器提供 get_loaded_kv_cache_group_ids(request)。基础实现返回可做前缀缓存的组；NIXL 与 Mooncake P/D 返回传输组；MultiConnector 向本次请求实际选中的连接器询问。这里的“声明”描述将恢复哪些组，不是传输已完成的证明。[5][6][7][8]

官方事实[4] ↗[9] ↗

协调器逐组调用外部计算块分配，把是否登记清零传入管理器。管理器拿到新物理块时就决定是否加入清零列表；环形块的分配也接收相同控制。修改没有把一个组的所有历史块永久排除，而是作用于这次外部加载所分配的新块。[4][9]

推导 / 教学示例

这一设计可以概括为：连接器说明写入范围，分配器掌握物理身份，调度器连接两者。执行期仍需要正确的完成通知、依赖顺序和失败恢复；单独这个接口不承担全部职责。

五 取舍和边界

推导 / 教学示例

不能用全局停止清零替代补丁。 新块可能携带先前内容，未被连接器覆盖的区域仍需要正确初始化。把所有清零关掉，可能让竞态消失却引入另一类未初始化读取。

推导 / 教学示例

更精确的接口也增加契约责任。 自定义连接器若声明过宽，可能让实际未恢复的组跳过初始化；声明过窄，则可能重新制造双写。代码审查应检查声明、真实传输描述符和组配置是否一致，而不是只检查接口存在。

推导 / 教学示例[13] ↗

本次修复不消除历史任务的顺序问题。 CPU offload worker 的代码仍要求加载流等待当前流：此前步骤已经发出的清零，不能靠本次分配时的决定撤回。换言之，空间上找对块与时间上排好顺序是两个条件。[13]

推导 / 教学示例

不存在本文证实的吞吐收益。 少做部分清零可能改变时间开销，但优化目标首先是正确性。不同模型、布局、传输和负载下是否影响延迟，需要另测。

六 生产排查

推导 / 教学示例

以下是基于机制推导的排查顺序，不是上游公布的通用故障诊断规则。

推导 / 教学示例
  • 固定部署身份：记录 prefill 与 decode 的镜像摘要、vLLM 提交、连接器、模型、缓存组配置和 block size。仅记录一个版本号不足以辨别自建镜像和回移补丁。
  • 确认相关条件：是否异步外部加载，是否存在需清零的组，是否使用窗口或环形布局，是否在重复请求中产生本地前缀命中。条件不符时，不要把异常直接归因于 #59504。
  • 保留最小失败请求及其执行元数据。在隔离环境记录 request、group、物理 block ID、分配批次、加载声明和清零名单。物理 ID 会复用，应把分配批次一起关联；无需把用户提示词写入普通生产日志。
  • 分别比较冷缓存和重复提示词。若只测冷启动，可能错过命中边界下的新分配；若只测热缓存，也可能掩盖其他初始化错误。
  • 修补候选先进入独立实例，以同一工作负载复验。不要为了排错同时改量化、并行度、图模式和连接器，否则难以判断变化来自哪里。
推导 / 教学示例

H20 集群可以复用上述观察方法，但本文没有 H20 特定复现实验。SGLang 的工程团队也可以检查同类所有权和异步顺序不变量；这不意味着 SGLang 存在同一缺陷，更不意味着 vLLM 补丁可直接移植。
