Ascend V2 心跳租约：延长 KV 保留，不等于证明迟到读取仍然有效

原文 2026-11-12核对 2026-11-13

11 月 12 日合入的 MooncakeConnectorV2 租约把固定等待改为默认 120/20/80 秒的保留与续租机制。完整解释 admission 盲区、通用 ACK、配置错配的 EngineCore 故障半径、取消后的在途读与实际回收边界；不把控制面续租写成数据面防陈旧保证。

推导 / 教学示例

这项变化值得关注，因为它改变了 P/D 分离的 KV 保留契约：已经进入 D scheduler 的请求，可以在等待调度或传输完成期间续租 P 上的源块，不再只能赌一个固定超时足够长。但“D 还在发心跳”“P 回了 ACK”“传输 API 返回成功”，分别回答不同问题。它们不能自动证明被读取的仍是原请求的 KV。

官方事实[1] ↗[2] ↗[3] ↗[4] ↗

主线 V2 无条件启用心跳租约，默认初始时长 120 秒、心跳间隔 20 秒、续租窗口 80 秒，配置必须 P/D 一致。旧 VLLM_MOONCAKE_ABORT_REQUEST_TIMEOUT 不再控制 V2，也没有回到原 480 秒超时的开关；V1 行为保持。

上线决策的两道独立门

推导 / 教学示例

先证明租约控制面能覆盖目标排队、取消和故障场景，再证明数据面在过期、源块复用和迟到 READ 时不会被误判。若后者没有证据，应明确限制支持范围并采用经验证的失败处理，不把通用 ACK 当成继续读取的许可证。

作者报告结果[7] ↗

作者直接注明：未增加 stale-read fencing 或逐请求数据面租约有效性检查，延迟 D 读取已经过期或复用的 KV，仍可能在传输层成功；没有新远程/NPU 推理与性能实验。本文据此不写“彻底解决过期读”或任何吞吐提升承诺。

背景：固定超时、可续租与真实进度是三件事

推导 / 教学示例

P 完成 prefill 后返回源 KV 位置，D 并不一定马上开始 READ。排队、KV 分配、worker 调度和网络传输都可能延后消费。如果 P 只按固定时间释放，D 仍然合法等待时源块就可能失效；如果 P 永远不释放，失联请求又会持续占据容量。租约用“最近收到的保留意愿”调和这两个风险，但保留意愿不等于请求取得了进展。

官方事实[2] ↗[4] ↗

登记从 D 的 on_new_request 开始，早于本地 KV 分配；仍在 EngineCore 输入队列、尚未进入 scheduler admission 的请求没有被心跳跟踪。P 在暴露 transfer params 前登记初始租约，并在返回参数中带 remote_kv_lease_duration。

推导 / 教学示例

独立线程让模型或 scheduler 等待时仍能续租，这是本次改善的核心，也形成一个新的运维问题：worker 永久卡住而心跳线程仍工作时，P 的租约可以一直延长。因此应分别观察 admission 前等待、admission 后等待、实际 READ 进度和心跳线程健康，而不是只监控进程存活。

机制：本地时钟、双到期队列与取消后的在途读

官方事实[2] ↗[3] ↗

P 使用自己的 monotonic 时钟决定有效期，不比较跨机器壁钟。设 duration 为 D，初始 expiry=now+D；正常续租只在尚未过期时将 expiry 延到 max(旧 expiry, now+floor(2D/3))。now>=expiry 视为到期，迟到心跳不复活旧记录。初始租约和续租租约使用两个按期限排列的队列，避免较长初始期限挡住另一队列更早到期的项。

120 / 20 / 80 的教学算例

推导 / 教学示例

假设 P 在 t=0 登记，且所有心跳刚好在 P 的 t=20、40、60 到达：初始期限为 120；前两次分别取 max(120,100) 与 max(120,120)，不缩短期限；t=60 才延到 140。若下一条在 t=140 恰好到达，则已到期，不允许复活。这是按源码公式推导的理想例子，不是网络交付保证或实测时序。

官方事实[3] ↗

D 按 P 的 host/port 分组并去重 remote request ID，每批最多 512 个，一个 peer 同时最多保留一条待 ACK 消息。ACK 时限为 1 秒，失败 peer 的连接在后续 interval 再尝试；慢 peer 不要求其他 peer 同步等待。旧 snapshot 的尾批要先 drain，再采新 snapshot，避免每到刷新周期就丢掉尚未发送的尾部。

官方事实[2] ↗[5] ↗

取消路径必须区分是否已经交给 worker。分配前取消会移除心跳，并通过尚未清掉的 do_remote_prefill 路径发送一次 DONE，随后清标志使重复 finish 幂等；已有在途 READ 的请求即使用户取消也继续续租，直到 worker 聚合完成。若本地 prefix hit 使 external token 为零，也会停止续租并通知 P。

官方事实[2] ↗

D 收到聚合 finished_recving 后先删除心跳登记，再排队通知 P；failed_recving 也走释放通知，因此 DONE 不是“推理成功”的标志。P 的到期处理只是把 ID 放入 finished_requests，之后 update_connector_output 填入 finished_sending，交给正常 delayed-free 流程。P scheduler 停顿时，不能把到期时间写成物理显存保证回收的时间。

官方事实[2] ↗[4] ↗[5] ↗

配置缓存是另一条独立路径：D 按 endpoint 缓存已通过的 engine_id/duration，TTL 600 秒、最多 1024 个 endpoint、LRU 淘汰，命中不延长 TTL；过期或淘汰后下次请求重新校验。缓存的是两端配置一致性，不是每个 request 的租约状态，更不是进程 incarnation 或 block generation。

取舍：续租更可靠，卡住的消费者也更能保活

推导 / 教学示例

初始租期从旧固定等待改为可续租机制，既能保护长等待，也可能让 admission 前的盲区更显著。调整 duration 需要连带观察“P 导出到 D admission”的尾部分布、heartbeat 批量发送耗时与 peer 故障重试。只看默认 120 秒是否大于平均排队时长不足以判断安全。

推导 / 教学示例

独立线程避免 scheduler 卡顿直接停止续租，但请求完全无进展时也可能继续保留 P 容量。这里不应简单停心跳强制回收，因为 in-flight READ 可能仍在访问源块；要先具备可验证的 transport 取消/完成同步或数据面防陈旧机制，再设计业务层超时处理。

官方事实[2] ↗

DONE 通知失败时，通知线程记录错误并结束该队列项，不无限重排；P 端将依赖租约到期，之后仍需 scheduler 消费完成队列。故不能承诺每个完成请求都即时释放，也不能用 DONE 队列为空说明源块已归还。

滚动升级比一个参数更重要

官方事实[4] ↗

P 必须先升级，代理要透传新字段，D 再升级并保持 duration 一致。缺失/不匹配错误发生在请求 admission，而不是服务 startup；“两个服务都能启动”不能替代真实 remote-KV 请求的兼容性探针。

作者报告结果[7] ↗

跨机 PP 与一个 P request 的多个独立 consumer 未经作者验证。当前保留与 DONE 按 request ID 处理，不能据此推导 consumer 引用计数安全；一个消费者 DONE 与另一个消费者仍在 READ 的组合，需要独立协议与回收证据。

服务收益成功且正确请求的TTFT/TPOT、错误率、P pinned blocks先达到预先登记 SLO；再比较长等待成功率、保留成本和峰值容量不符合 SLO 则不以续租次数或ACK率宣称优化成功待验证
推导 / 教学示例

把“租期到期后多久回收”拆成到期检测、完成队列消费和物理释放三段；把“长请求被保护”拆成 admission 前等待与之后实际续租覆盖。这样的口径才能发现一个实现同时改善平均等待成功率，却在输入队列或永久卡住的 worker 上留下另一种风险。
