结论 物理页复用要等旧读完成

推导 / 教学示例

这次值得关注的不是新增一项分配器性能开关，而是 lazy free 的安全前提被收紧。对生产排查，首先区分“逻辑引用已移除”和“设备不再读这块内存”。如果服务在内存压力、回撤或淘汰时出现难以复现的输出偏差，应该把物理页的代际交接纳入时间线，而不是只核对 radix 树和可用容量。

官方事实[1] ↗

11 月 6 日 01:22 UTC，#48450 以 7a82e415 合入 main；补丁仅修改 Band 文件，未增加测试文件。

官方事实[2] ↗

修复是在 CUDA lazy free 路径、存在已记录事件时，对当前流加入 latest-forward 完成等待，再解除映射及回收物理页。

推导 / 教学示例

建议把这项变更列为启用统一内存和 lazy compaction 部署的定向正确性核查，而不是直接作全量升级结论。验收必须同时证明事件覆盖真正的最后一次旧读、等待传递到复用写入，以及业务输出没有偏差。只看到补丁存在、单测名称或 free 返回，都不足以完成这三件事。

待验证

本报告未运行 GPU 推理、上游测试或服务压测。新增等待的性能代价、真实产物是否包含修复、特定模型后端的事件覆盖均待验证。

背景 页表准备完不等于注意力读完

作者报告结果[7] ↗

作者描述的触发条件是统一内存的 lazy compaction，运行中 forward 遇到分配压力驱动的回撤或树淘汰；提前复用可能让旧 forward 读到已清零的 KV。作者未报告速度测量。

推导 / 教学示例

把一次注意力执行拆开看：调度器先决定请求的逻辑位置，页表准备把逻辑位置变成物理位置，GPU 内核随后按这些位置读 KV。中间结果一旦变成设备可使用的地址表，旧的虚拟映射是否还存在就不再决定该次读会不会发生。逻辑引用计数可以已经归零，硬件读访问仍可能没有完成。

推导 / 教学示例

这与传统 CPU 对象生命周期有相似之处，但不能照搬“函数返回就没人使用”的直觉。GPU 工作是排队执行的，Python 调用了释放函数，只能证明主机执行到这一行。地址表、KV 数据、事件和分配器计数属于不同对象；需要把它们连接到同一轮请求、同一物理页和同一执行流才能判断谁可以先动。

推导 / 教学示例

本题与前一篇草稿 KV 路由报告不同。路由报告检查“本层应该使用哪个地址空间的行号”；这里检查“一个物理地址可以从旧使用者交给新使用者的最早时刻”。地址空间选对不排除时序错误，释放时序正确也不排除选错子池。两类测试应独立保留，不把新补丁当成旧问题的重复发布。

机制 用完成事件连接旧读和新写

官方事实[3] ↗

Scheduler 把共享读栅栏与 forward 完成事件分开处理；后者在 worker forward 返回后、结果回传前记录到 forward stream，并交给统一分配器。

官方事实[4] ↗

ChainAllocator 将该事件传给所有成员。写集元数据另行传递，Mamba 成员的 out_cache_loc 分支与 token 成员不同。

官方事实[9] ↗

作为 API 语义参考，PyTorch v2.9.0 的 wait_event 约束该流之后提交的工作，调用本身不等待事件完成；因此它是设备间的顺序依赖，不是把主机锁住直到 GPU 空闲。

推导 / 教学示例

用三个动作描述最小安全条件：R 是旧代最后一次读 P，E 是覆盖 R 的完成事件，W 是新代第一次破坏旧内容的写 P。期望得到 R → E → W。这里“破坏旧内容”包括清零，不只包括写入新 token。若仅有元数据读取 M 已完成，M → W 并不能推出 R → W，因为 R 可能在 M 之后才使用之前形成的物理地址。这个缺口正是需要额外依赖的地方。

推导 / 教学示例

“最新”也有前提。如果旧读均排在同一 forward stream 上，而所用事件在它们之后记录，较新的事件可以覆盖前面的读；如果某个后端把读取转移到另一条没有汇入的流，仅靠事件名字不能证明覆盖。生产分析应核对真实发射流和事件记录点，不把函数调用栈当成设备执行顺序。

推导 / 教学示例

等待放在回收动作之前，还意味着应分开观察主机队列和设备数据。主机可能已经更新计数或拿到代表新列表的张量对象，但这些对象对应的 GPU 内容尚未计算完。只要所有消费者遵守同一流或显式依赖，这并非错误；错误发生在某个消费者绕开依赖，把“主机已返回”解释成“物理页可写”。

推导 / 教学示例

这条依赖不替代其他生命周期约束。一个物理页可能还有传输、压缩搬迁或别的执行器使用者；完成事件只为它实际覆盖的工作提供证据。若后续扩展分配器、增加 side stream 或异步传输，应重新画出消费者集合，并明确哪个事件覆盖哪一组，避免沿用过期假设。

取舍 更强顺序可能减少调度重叠

推导 / 教学示例

新依赖的直接成本由“等到了多少尚未完成的旧工作”决定，而不是由 wait_event 调用的主机耗时决定。当压力释放很少发生，新增依赖可能不常进入关键路径；当大量请求频繁回撤并立即重新分配，调度流后续 GPU 工作可能多次等待。两种负载应该分开统计，平均每秒 token 可能把尾部损失隐藏掉。

推导 / 教学示例

同样不能把它概括为“free 路径从此没有主机同步”。该补丁新增的是流等待；原本其他步骤是否需要主机参与，是另一项性质。为估算影响，应分别记录主机调用时间、事件尚未完成的等待区间、等待之后的设备排队，以及最终请求的首 token 和逐 token 延迟。

真正的优化方向应在正确性证据之后讨论。更细粒度的页级退休有机会缩短等待，但会引入每页读者归属、事件聚合、重用代数和回收积压管理。未经测试的“更精准”等待可能漏掉消费者，也可能因维护开销得不偿失。本报告不提出删除 whole-forward 等待来换取漂亮的微基准。

生产排障 追踪页的代际而不是只看容量

推导 / 教学示例

以下是原创故障假设，不是已确认的用户事故。排查时给物理页增加代际标识：同一个 P 第一次属于请求 A，复用后属于请求 B。日志至少要能把请求、逻辑页、物理页、代际、事件身份和执行流连起来。否则“释放了一页”和“读坏了一页”可能指向同一地址的不同生命周期，时间线会被错误拼接。

如果只能采集少量数据，优先保留发生错误前后的环形事件记录和所涉页的校验摘要，而不是持续记录完整 prompt 或 KV。使用合成输入做确定性复现；生产观测只保留定位所需的匿名标识、长度、时间和内容摘要，避免把敏感用户文本写进调试包。

临时处置必须以现有能力为边界。可以选择已验证基线、降低并发或暂停新增放量；不要承诺关闭某个开关一定能透明恢复，也不要在受压服务上随意插入全设备同步。调试同步可能掩盖竞态，同时改变吞吐和超时行为，应在隔离环境中先验证。

推导 / 教学示例

构造延迟时不要让调度流等待的事件依赖调度流自己未来才会提交的“解锁”操作，这会把测试变成死锁。可用有限时长设备任务或预先安排、可独立完成的流工作扩展窗口，并设置外部超时。测试必须先证明旧版确实具备可触发的窗口；若旧版也始终通过，应报告“未触发”，不能声称修复已被验证。

推导 / 教学示例

既有单元测试仍有价值，应先在匹配依赖环境运行，再补新增 GPU 回归。CPU 测试适合验证集合、映射和模拟事件账本；真正的设备顺序实验需要读取时间线和内容见证。把二者都保留，可以避免以后有人为消除性能回退删掉等待，同时单元测试仍然全部通过。

失败退出超时、缺失事件、数据错或 SLO 退化的处理停止扩大流量，保留证据，回到已验证基线待演练待验证
推导 / 教学示例

样本量应由系统风险和可用测试时间决定，而不是为了写出一个整数。零异常只意味着在已经执行的样本内未观察到错误；报告应同时列有效竞争次数、持续时长和配置覆盖。对于尾延迟，用相同到达率及长度分布重复多轮，并报告分位数和不确定范围，避免把一次抖动称为性能回退。

推导 / 教学示例

上线结论建议写成带范围的句子：某产物、某后端、某模型和某组内存配置，在指定压力窗口内通过数据、顺序、输出和服务预算。不要简化成“SGLang 已修复所有统一内存问题”，也不要把修复后不再崩溃写成缓存正确性的充分证据。
