推导 / 教学示例

对 H20 推理运维，这次升级最重要的并不只是某个吞吐数字：失败请求的迟到 KV 写入可能影响后续请求，PP 边界也可能传递尚未完成的计算语义。与此同时，缓存核心、PP 投机和 MoE 默认路径发生变化。已发布是版本收录的证据，仍不能替代自己的正确性、故障隔离和负载回归。

官方事实[1] ↗

本文涉及的 PR 均被 v0.5.21 正式发布页收录。判断“这个版本是否包含”时使用发布清单，而不只凭 PR 已 merged；后者未必能证明某个镜像或安装包的实际代码。

推导 / 教学示例

建议沿同一条排查顺序读变更：数据属于谁 → 计算是否完成 → 优化究竟省了哪段时间。先回答资源释放和跨卡交接为什么安全，再用自己的请求分布证明性能收益。

背景：三个结束事件必须分别证明

推导 / 教学示例

P 处理输入并产生 KV，D 读取 KV 进行生成。P/D 跨实例交接状态，TP 涉及层内计算，PP 将不同层放到不同阶段。异步传输、延迟归约和页面复用让“请求结束”“计算完成”“资源可复用”成为三个必须分别证明的事件。

推导 / 教学示例

用户看见一次失败，并不说明所有 rank 已停止写入；GPU 上得到一个张量，并不说明它已经完成归约。质量异常与低利用率高延迟，都可能来自边界语义而不是模型权重或纯粹的网络带宽。这里提供的是公开机制上的原创排查框架，不映射任何公司内部事故。

五项机制：生命周期、语义与控制回路

机制一：P/D 失败必须覆盖在途写入

官方事实[2] ↗[3] ↗

#41023 将受支持后端的 D 侧 KV 延迟释放设为默认；#41404 又把保护扩展到 P 故障、传输错误等非 D 主动取消的路径。失败上报时，其他 rank 仍可能处在写入过程中，故障分支需要保留这个事实。

官方事实[2] ↗[3] ↗

支持范围包含 Mooncake / NIXL，Mori / fake 没有相同默认行为。#41023 记录默认等待 30 秒，旧式 ACK 混合版本可能等到超时。确认没有写入者才是释放的安全条件，请求失败本身不是。遗漏延迟释放分支，不能靠调大超时解决。

推导 / 教学示例

取消潮可能暂时压低可分配容量。应把故障率、保留页、ACK 等待与排队放在一起分析，不能把占用上升直接作为关闭保护的理由；超时也不是物理写入已经结束的证据。

机制二：PP 传递的是计算语义，不只有张量

官方事实[4] ↗

#41079 修复的历史缺陷是：FFN all-reduce 延至下层融合执行，待归约语义未在 PP 交接中正确保留，接收方可能把 TP 部分和当作完整结果。该 PR 在相关发送前补归约。

官方事实[5] ↗[6] ↗

最终版本不能一概手工给 PP 发送加 all-reduce。同版 layer_boundary 重构集中表达残差、输出所有权和待完成工作；官方指南还区分动态待完成状态与可以按静态契约跨阶段传递的部分和。原则是归约责任既不丢失，也不重复，当前文档必须对照安装版本。

推导 / 教学示例

没有 NCCL 错误，也可能存在通信语义错误。若只在特定 PP×TP 组合中出现精度下降，应核对归约和残差责任，再判断权重或数值 kernel；不能只看 collective 是否成功返回。

机制三：Rust 缓存核心改变控制面

官方事实[7] ↗

#39627 将统一树的默认核心转到 Rust，并集中 Python 回退，还涉及淘汰、锁和缓存状态语义。

推导 / 教学示例

CPU 缓存维护是瓶颈时，这项变更值得测；GPU 或网络主导的服务未必获得同样整体收益。不要编一个固定加速比例。至少分别测试冷缓存、共享前缀和持续淘汰，记录实际核心、CPU 时间、命中与回收；固定淘汰策略便于归因。

机制四：PP 投机新增跨阶段控制回路

官方事实[8] ↗

#30775 通过 SGLANG_ENABLE_PP_SPEC=1 显式启用。草稿位于最后阶段，下一轮树与接受信息回传，各阶段参与验证，而不是每个 stage 复制一份草稿。

作者报告结果[8] ↗

该 PR 的测试使用 PCIe、无 NVLink 的 RTX PRO 6000 Blackwell，并指出关闭 overlap 调度的限制；不能把结果直接套到 H20。TTFT、ITL、吞吐和接受长度要分别测。

推导 / 教学示例

如果质量正常但收益消失，先核对接受长度与回传，再从时间线拆草稿、验证、通信和流水空泡。接受率高不等于端到端快，新增控制回路可能消耗原本期待省下的时间。

机制五：MoE finalize 默认是一项数值取舍

官方事实[9] ↗

#40105 将受开关控制的 FlashInfer MoE fused finalize 默认关闭，可用 SGLANG_FLASHINFER_MOE_FUSED_FINALIZE=1 启用；它不覆盖所有 MoE，PR 也没有新增 GPU 精度实测。

推导 / 教学示例

升级后的速度变化，可能来自默认数值路径改变。应把 finalize 开关作为单独实验，比较任务分数、数值差和延迟，不能凭几个回答“看起来相同”就恢复旧设置。

发布证据与 H20 结果边界

作者报告结果[10] ↗

#38913 为 GLM-5.3-Flash 提供 H20 block-FP8 Triton MoE 配置。作者报告在 8×H20、TP8 / EP8、1024 输入和 1024 输出、并发 16 下，输出吞吐增加 23.8%。每个变体为 64 请求，仅一组成对运行；微基准不包含 EP 通信。

推导 / 教学示例

这说明该组合值得复测，不证明所有模型、上下文和网络都有相同收益。4 卡与 8 卡若处于不同节点或条件，不能当成受控扩卡曲线。

取舍：默认更安全，也可能改变资源曲线

推导 / 教学示例

延迟释放会在故障期间暂留资源，换来跨请求隔离；归约契约会改变结果的生产与消费位置，换来更清晰的正确性责任；缓存核心改变 CPU 维护路径，但不能抹去 GPU 和网络瓶颈。每一项都需要把代价与收益放回同一张请求时间线。

推导 / 教学示例

PP 投机增加树和接受信息的跨阶段控制，MoE finalize 的默认变化体现数值与执行路径的取舍。升级时同时改变所有开关，即使得到更快或更慢的结果，也很难解释原因。先比较新版默认，再逐项选择可选优化。

推导 / 教学示例

对用户负载尚未证明的收益，应写成合理预期或待验证。尤其不能把作者的一次 H20 成绩外推成业务稳定收益，或把发布清单里的修复当作混合版本滚动升级的完整承诺。

故障关联：从症状回到边界责任

原创故障假设，不代表真实生产事故
症状机制假设优先证据依据
取消 / 传输失败后，无关请求质量异常迟到写入与页复用交叉，或故障分支漏过延迟释放。请求 / room / 页身份、每 rank 写入、ACK 及释放顺序。待验证
取消潮后 KV 占用升高、排队变长保护期间页暂留，或确认迟迟未到。故障率、保留页、ACK 等待、可分配容量和旧版本互通。待验证
特定 PP×TP 组合精度下降但无 NCCL 报错归约 / 残差责任在边界丢失或重复。边界状态、归约次数、logits 差与任务分数。待验证
升级缓存核心后 CPU 或尾延迟变化实际核心、回退、淘汰与命中行为不同。冷暖缓存分组、核心身份、回退原因、CPU 与 KV 状态。待验证
PP 投机质量正常但加速消失草稿、验证、回传或流水空泡抵消收益。接受长度、迭代时间线、通信与 KV 占用。待验证
MoE 升级后速度变化受控 finalize 默认数值路径变化。开关、任务分数、数值差与相同负载延迟。待验证
推导 / 教学示例

优先保留配置与时间线，确认异常在哪个边界发生。性能告警和正确性告警应分别处理，尤其不要为了快速恢复吞吐而在未理解页所有权前关闭保护。

隔离验证矩阵：一组实验回答一个问题

待验证

所有实验固定权重、量化、驱动、库、拓扑和请求集，冷暖缓存分开，重复成对运行。确定性场景比较 token；非确定性场景比较误差分布与任务分数。数值容差、质量门槛和故障预算在实验前定义，不编通用可接受下降百分比。此矩阵不是官方已覆盖用户环境的测试结果。

原创隔离验证矩阵
实验组对照与唯一变量主要观测验收条件依据
PD 故障同配置分别测取消、发送方故障、传输失败和正常对照。无关输出、页所有权、ACK / 释放时序、恢复。无跨请求污染或提前复用；恢复满足既定故障预算。待验证

MoE同版本一次只切 finalize 或 tuning。数值、任务分数、TTFT、TPOT、吞吐。质量先过门槛，再按业务延迟预算选择。待验证

上线顺序与指标验收

推导 / 教学示例

建议采用“旧基线 → 新版默认 → 单项可选优化 → 小流量灰度”的顺序。质量异常先保存配置和时间线再回滚。灰度不是代替隔离测试，而是验证业务请求分布下是否仍满足已定义的门槛。

验收记录：同时覆盖正确性、隔离与收益
维度应保留的记录通过条件依据
版本归属SGLang commit / 镜像 digest、依赖锁、模型与草稿 revision、启动参数。可以从运行实例追到发布清单和实际实现。待验证
状态正确性请求、页、room、rank 的生命周期与确认时间线。故障期间无跨请求污染，无提前复用。待验证
计算正确性边界责任、归约次数、数值误差分布与任务分数。按预定义容差通过；不能漏算或重复计算。待验证
服务 SLO逐请求 TTFT / TPOT / ITL、错误率、负载分布与样本数。代表性负载及长尾满足事先约定的预算。待验证
资源与收益总 GPU、CPU、KV 保留量、吞吐及重复成对结果。质量稳定后收益仍超过噪声，且回退路径可解释。待验证

结论分级与待验证清单

推导 / 教学示例

已确认：本文所列变更被正式发布清单收录，并有对应 PR 或指南证据。合理预期：故障隔离、边界语义和可诊断性，比单个速度数字更能帮助建立可交付服务。尚未验证：实际 H20 收益、混合版本恢复、业务精度和长上下文长尾容量。

待验证
  • PD 取消请求或传输失败后，KV 是否正确释放，滚动升级期间是否出现额外占用或请求错误？
  • Mooncake / NIXL 的 ACK、超时及不同版本互通是否满足自己定义的恢复预算？Mori / fake 路径不得假定相同默认行为。
  • 实际部署的 layer_boundary 契约是否让归约责任既不丢失也不重复？不要机械给所有 PP 发送添加 all-reduce。
  • 业务的冷缓存、共享前缀与淘汰负载是否真正受益于 Rust 核心？回退是否可观测？
  • PP 投机与 finalize 选择是否在自己的 H20、网络、采样和负载下通过质量与长尾门槛？
推导 / 教学示例

核心能力不是记住哪条 PR 变快，而是解释资源释放和跨卡交接为什么安全，然后证明优化帮助了自己的负载。
