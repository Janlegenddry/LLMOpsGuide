LMCache v0.5.8：SGLang MP 恢复后，先对齐各 rank 的写入进度

原文 2026-11-22核对 2026-11-24

核对 v0.5.8 标签确实包含 #6659。它让心跳恢复标志经原有 MIN 同步，避免不同 rank 各自清游标而走向不同的 store／collective 序列。不是共享 L3 的对象可见性修复。

作者报告结果[1] ↗[2] ↗[3] ↗[4] ↗

v0.5.8 发布说明列出 #6659；我用 GitHub 比较和冻结 connector 双重核对，确认合入提交已在标签源码内。恢复回调只立标志，调度轮询在既有 MIN 上对齐何时清除 store 进度。这里修的是并行参与者的决策次序，不是 SGLang HiCache 共享 L3 的数据可见性。

推导 / 教学示例

如果你负责灰度，先证明各 rank 对同一请求的写入、跳过、回退决策一致，再看 TTFT。仅看到 /health 恢复或一次远端命中，不足以放量。

问题背景：不同 rank 可以在不同时间发现 MP 服务恢复

作者报告结果[2] ↗

引擎侧 SGLang Unified Radix Cache 使用 LMCache 多进程 connector。独立服务重启时，connector 必须恢复传输上下文。旧行为在每个 rank 各自收到恢复时清除已提交 token 游标；同一已知前缀可以因此在 A 变成待写、在 B 仍无新后缀，而两边随后进入不同的 collective 序列。

推导 / 教学示例

这条风险最适合多 rank、稳定前缀多轮扩展、MP 服务半故障恢复的工作负载。单 rank 没有跨 rank 次序问题，但可用于检查游标语义和重新注册；大流量中的类似超时也可能来自传输/后端而非本机制。

机制：把“是否保留进度”并入已有就绪归约

作者报告结果[2] ↗[4] ↗

标签代码先算连续 ready 操作数，再在 heartbeat lock 内读走本地 reset 标志；原 CPU int64 张量从一个元素变为两个：[ready_count, keep_progress]。原有 MIN 在启用的 TP、PP 组先后执行。任一参与者送入 0，本轮该值归约为 0，所有参与者清除 _store_submitted_tokens。ready 前缀仍取第一项，未新增归约调用。

推导 / 教学示例

用两 rank 的 [2,0] 与 [1,1] 作教学例子，结果 [1,0]，并非丢弃 ready 的第一项，也不是重新写完 1 个 chunk。若所有 rank 送入 1，只保留游标；无故障时仍可按对齐后的后缀增量提交。

取舍：补齐状态边界，不夸大恢复承诺

作者报告结果[1] ↗[5] ↗[8] ↗[9] ↗

MP 将这条接入的跨进程资源、重注册与传输边界显式化，并把共享 client/common/transport 抽成模块。旧 InProcess 移除是仓库和迁移边界；NIXL 分包或 CUDA wheel 选择则是安装边界。不要因为提供者同样写着 KV Cache，便把这三件事归因为同一次数据一致性修复。

作者报告结果[4] ↗[6] ↗

本地提交游标不是远端已持久化的连续覆盖范围。#6404 针对普通 store 失败：当后续 chunk 已提交，也把重试起点回拨到最早失败范围，而 #6659 针对恢复后全组重置；前者不能替代后者。共同重写也可能增加冷前缀重算/传输，增量成本未测。

推导 / 教学示例

与共享 L3 区分：共享后端关心谁何时能看到对象、TTL 或索引，本文关心 SGLang→LMCache MP connector 的本地调度游标与跨 rank collective。即使后端相同，也不能用其中一项验收替另一项背书。

排障：以同一逻辑请求的 rank 差异定位

推导 / 教学示例

若仅在远端服务恢复后出现停顿，应同时检查每 rank 的注册成功时间、轮询轮次、是否清游标、store 起止范围、提交还是跳过、collective 类型/序号以及最终请求结果。前三项均可对而仍有后端数据错误，故将读取校验、传输完成和客户端终态单列。

推导 / 教学示例

不要用正常的 ready_count=0 判定死锁。先证实某一 rank 进入不同 collective 序号或跨过限定时间仍未推进，再看同一请求是否因游标边界不同分叉。生产诊断只保留必要的去标识化追踪，不采集原始 prompt。
