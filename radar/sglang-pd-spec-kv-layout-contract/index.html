结论 先约定草稿 KV 的含义，再讨论传输是否成功

推导 / 教学示例

对于预填充与解码分离的投机部署，传输完成只能说明某些字节到达目的地，不能保证接收者用相同的规则解释它们。本次值得新增一道上线门：在同一组 P/D 实例开始配对前，记录双方是否发布 draft KV 布局、各自的算法和 entry 数，并把明确不匹配当成配置错误，而不是网络抖动。

官方事实[1] ↗

#48375 于 2026-11-07 合入主线，冻结提交为 043cfc4d3a2cc2a931d15862f08c4b60b692c957。它增加 spec_kv_layout 声明与匹配检查，涉及 Python 连接管理器、Python/Rust bootstrap 和定向测试。本报告不据此认定任何正式版本或运行镜像已包含变化。

推导 / 教学示例

最容易读错的是三种状态：{} 不是 None，布局缺席也不是“确定兼容”。这一区分既让 target-only decode 拒绝已声明的 DSpark/DFLASH draft KV，又避免误拒没有 draft entries 的流水线 rank。升级时优先证明控制面的兼容矩阵成立，再做真实数据面和服务验收。

推导 / 教学示例

  • 不应直接外推：所有投机算法、所有 DSV4 state-only 布局、checkpoint 身份校验、不同 TP/CP 的全局可兼容性。
  • 当前完成：原始 PR、直接父版本和合入源码核对；51 个抽取源码逻辑案例通过。GPU、完整上游测试、Rust 执行与生产测量均未做。

背景 同形的缓冲区未必承载同一种草稿上下文

作者报告结果[6] ↗

作者解释 DSpark/DFLASH 的 prefill 会从 target hidden states 生成 draft context KV，而 decode 不能只靠传来的 token 元数据重建这些字节。因而两端对 draft KV 的算法或 entry 数理解不同，不能仅靠传输成功来消除风险。

推导 / 教学示例

可以把 PD 交接拆成四层：地址能否访问、字节是否完整、布局是否对应、模型语义是否正确。网络后端主要解决前两层，布局声明补充第三层，但并不自动覆盖第四层。工程上的危险是把四个不同的判断压成一个“请求成功”：数据没有被截断，却仍可能被错误地解释。

推导 / 教学示例

一个教学反例是两端拥有一样大的接收区，却把某几段解释成不同算法的草稿上下文。缓冲区大小相等、传输字节计数相等、bootstrap 可访问，三者都不能推出模型行为一致。另一个反例则相反：某个 PP rank 没有草稿层，如果强迫它提供和其他 rank 相同的本地 KV 条目，就会误伤合法拓扑。两个反例共同要求协议表达“已知不使用”与“本 rank 没有这类数据”的区别。

官方事实[2] ↗

这次新增的布局键仅含 algorithm 与 num_draft_entries。源码明确不把 block size 加入这一声明，因为这里的 prefill draft KV 按 token 写入；DSV4.1 的 SWA 环形布局仍由独立校验处理。不能把该简化解释为所有模型的 block size 都可任意不同。

推导 / 教学示例
  • 明确算法名称是必要条件之一，而不是 checkpoint 等价的充分条件。相同算法与 entry 数仍可能使用不同权重或其他未覆盖配置。
  • 升级前建立运行产物清单：P、D、bootstrap 后端、各 PP rank 的角色和真实镜像摘要。不要只抄启动命令。
  • 将“不受本次检查覆盖”单独记录，不要和“已验证匹配”共用绿色状态。

机制 本地三态、聚合首值与解码前置拒绝

官方事实[2] ↗

布局函数对非 DFlash-family 模式返回 {}，对该家族但 num_draft_entries 为零的 rank 返回 None，对有 draft entries 的 rank 返回算法名与 entry 数。这些是本地状态，不是三种不同的网络载荷。

官方事实[3] ↗[4] ↗

Python 与 Rust bootstrap 都保留首个非 None 布局，之后缺席布局的 rank 不会抹掉它；只有两个已知布局冲突时才拒绝。这样既允许 draftless PP rank 先注册，也允许它后注册。它表达的是当前聚合声明，而不是对每个 rank 的完整模型拓扑证明。

官方事实[3] ↗

Decode 的新比较条件是两端布局均非 None 且字典不同。异常发生在 _resolve_rank_mapping 和 prefill_info_table 写入之前。除此之外，decode 现在只将已知字段送入 PrefillServerInfo，避免新增的未知响应键直接破坏构造；成功获取过的地址仍有缓存快路。

推导 / 教学示例

因此应分开观测四个事件：注册表接受某个 rank、GET 返回可用拓扑、decode 接纳该拓扑、真实请求完成。注册表接纳不代表 decode 必须接纳；decode 通过这道门不代表后续数据无误。已有缓存快路也提示，测试重配置时要确认实际触发了重新获取，不能仅修改远端字段后重复一条已缓存请求就声称新规则生效。

官方事实[8] ↗

还有一处与 PR 摘要措辞需要区分：最终源码的 PUT payload 显式包含 spec_kv_layout: null；GET 则在聚合值为 None 时省略该字段。所谓普通 PD“无新布局”应理解为没有非空布局声明，而非请求 JSON 字节完全不变。新增请求字段测试也直接断言该 key 存在且值为 None。

推导 / 教学示例
  • 不要把 {} 替换成 None 来让错误消失。两者在 decode 端有不同的保护含义。
  • 不要从 GET 缺字段推断 P 端有或没有草稿 KV；旧版本、target-only 与 draftless 都可能没有声明。
  • 不要扩大 num_draft_entries 的含义。它不是生成 token 数、接受长度、迭代步数，也不是通用 checkpoint 指纹。

取舍 兼容性保留了旧路径，也保留了未知区

推导 / 教学示例

这是一道按字段存在性开启的检查，而不是要求所有旧实例立刻升级的新强制协议。它减少旧组合被无故拒绝的概率，代价是远端未发布字段时无法提供新的布局保证。因此“连接仍能建立”与“保护已经启用”必须是两张不同的验收表。

官方事实[7] ↗

直接父版本把整个响应字典交给 PrefillServerInfo 构造，且没有 spec_kv_layout 字段；新版本先过滤未知字段。新 prefill 向旧 decode 发布非空布局时，旧构造会遇到未知参数并走获取失败处理。与其泛称滚动兼容，不如逐项验证谁先升级、谁保留旧实现、是否实际发布该字段。

推导 / 教学示例

过滤未知字段有扩展性收益，也有清晰边界：它只是减少结构解析失败，并没有让旧消费者自动理解未来字段的安全语义。若未来字段改变必需的 KV 解释方式，就不能因为“JSON 能读”而默认协议已经成功协商。

观测数据应保留角色而不仅是主机名。尤其在 PP 中，同一服务的一些 rank 有 draft entries，另一些没有；把所有空值压成“未启用投机”会制造错误的排障路径。建议日志分别记录算法、entry 数、值分类、后端、rank 与实际产物身份，在不记录请求正文的前提下即可诊断大多数控制面差异。

推导 / 教学示例

拒绝策略也要分层：明确 mismatch 是配置拒绝，短退避无法改变其含义；连接暂不可达和拓扑尚未 ready 则可能是启动顺序问题。实验应检验路由器是否把拒绝暴露为可理解的错误，避免把流量不断重派给同一不兼容配对。是否需要隔离实例取决于实际运维方案，本报告未替用户改动任何路由。
