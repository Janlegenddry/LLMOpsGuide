官方事实[1] ↗[3] ↗[4] ↗

FlashInfer #6144 已于 10 月 13 日 16:10:42 UTC 合入。它把投机解码验证阶段的等长 query 信息交给规划器，并新增一条受严格约束的 SM90 FP8-KV 实现。固定合并提交为 a8e747c3c1f7dfe5d51fab3883824b15da6829b7。

推导 / 教学示例[7] ↗[8] ↗[9] ↗

运维上应把它拆成三个问题：服务调用方有没有传信息；规划器有没有利用信息；最终执行的是哪条 kernel。三个问题都不能用“已经升级 FlashInfer”来代答。当前读到的 v0.7.1 与 v0.7.2rc3 固定文件没有这项实现；对应 SGLang EAGLE 接线 PR #44115 仍开放。

推导 / 教学示例

对 H20，合理动作是建立小范围候选验证，而非把 H200 作者成绩写进容量计划。设备能力、每 rank 形状、量化语义、图执行路径和实际产物缺一不可。本文的主要价值也不是复述加速比，而是把这五项变成可否决的准入条件。

两级收益不能混算

推导 / 教学示例

第一层收益来自更准确的计划，第二层才来自专用实现。为区分二者，建议设计三个实验臂：A 不传提示；B 传提示但禁用专用实现；C 提示与专用实现同时启用。其余输入、模型、调度策略和图桶保持一致。

作者报告结果[2] ↗

作者报告在 8×H200 的特定 agentic 工作负载中，组合方案相对控制组 ITL p50 下降 19.4%、输出吞吐上升 6%；这是作者结果，非 H20 实测。作者同时声明性能测量基于较早发布分支后再迁移到 main，因此数据与当前制品不能直接画等号。

推导 / 教学示例

分析上，单次 attention 减时只能减少它占据的那部分请求时间。服务总延迟还包含排队、其他算子、通信与调度。某个 kernel 的倍数提升无法直接乘到整机吞吐。更值得关心的是 B→C 的边际收益能否覆盖额外 JIT、工作区、图生命周期与回退复杂度。如果 B 已达到 SLO，C 的价值需由实际流量证明。

机制：等长信息在哪里丢失

推导 / 教学示例[5] ↗

通用 paged attention 接口用前缀和描述各请求 query 区间。这个表达能容纳不等长请求，却不会自然承诺每次图重放都等长。固定 scheduler 源码在图模式下区分“有等长承诺”和“没有承诺”两条 tile 规划路径。

推导 / 教学示例

原理解读：假如一批请求在验证阶段各有相同数量的候选 token，接口只交出一个可变长容器，相当于把业务已经知道的约束丢给下游重新保守估计。新提示不是创造新的模型知识，而是把一个调用方可验证的不变量显式传递下去。这里重要的不是参数短，而是承诺必须贯穿每次计划和图的使用周期。

推导 / 教学示例

机制分为三个职责层：

推导 / 教学示例
  • 服务层：验证批次 → 构造 query 边界 → 核验每个请求长度
  • 规划层：提示缺失/不成立 → 通用规划；提示成立 → 更精确的 FA2 规划
  • 执行层：通过全部专用条件 → split-KV attention → 同 stream merge；任一条件不成立 → stock 路径
推导 / 教学示例

调用方接线尚未合入，库的能力不能误读成生产默认。CPU 计划/捕获与 GPU replay 是不同执行阶段，不能理解成每次 replay 重新检查 Python 条件。

官方事实[3] ↗

下图仅画 CUDA Graph 模式。Eager 模式不会向 FA2 规划器转发这项图规划提示，但专用入口会独立核验 host query 长度，仍可能命中专用实现。因此不能把 FA2 收到非零提示当作所有执行模式下的专用入口必要条件。

图与回滚：Python 开关不等于已捕获图的热切换

推导 / 教学示例[1] ↗[3] ↗[4] ↗[10] ↗

固定实现将准备工作放到计划阶段，专用计算与合并形成两个 stream-ordered kernel；入口存在禁用开关 FLASHINFER_DISABLE_EAGLE_VERIFY_FP8KV_SM90。 CUDA 官方说明，图定义与执行相分离，实例化后可以反复启动已定义的操作。

推导 / 教学示例

据此推导的运维要点：若专用 kernel 已被捕获进 graph，仅改变 Python 进程环境不能据此断言现有 graph 节点已经替换。可靠回滚应走服务框架支持的停流、排空、重新计划/捕获或进程替换流程，再用 trace 验证 stock 节点。反过来，若首次捕获走了 fallback，后来准备好 JIT 也不意味着旧图自动升级。

推导 / 教学示例

Python dispatch 计数更适合证明普通调用和捕获时选择了什么，不能未经验证地当作每次 GPU replay 的执行次数。监控应把“命中过专用入口”和“生产 token 实际由专用图执行”分开。

推导 / 教学示例

此外，回退必须发生在安全边界。运行前 guard 失败可以转 stock；GPU 已经发生执行故障时，不应假设重复跑一个 stock kernel 就能修复进程状态。本文没有看到足以支持“所有运行错误自动恢复”的证据，不能如此宣传。

正确性：从“结果接近”走到业务可接受

推导 / 教学示例[6] ↗

固定测试同时覆盖 guard、数值参考和图捕获路径；测试文件中的参考误差门限、对 stock 的相似度门限，与 PR 描述中的作者实验指标不是同一套验收量。 不应把两者混写成已经证明逐 token 一致。

推导 / 教学示例

本站建议验收分四层，而非只跑一份问答集：

推导 / 教学示例
  • 张量层：记录有限值检查、误差分布和异常 mask；零有效元素、边界页、奇数 split、长短上下文混合都应有预期处理。
  • 算法层：检查 draft 接受长度分布、拒绝位置和回退频率；仅平均接受长度一致会掩盖少量长尾异常。
  • 模型层：用配对输入比较任务成功率和输出长度；允许浮点路径变化并不等于允许业务质量无界漂移。
  • 服务层：固定超时/错误预算，检查不同批次、并发和 graph bucket 是否存在集中失败。
推导 / 教学示例

所有新增验收是本文建议，并非声称上游已经覆盖。测试通过也不能证明任意业务流量安全。验收应保留原始请求集合、随机种子和两组输出，便于定位某一类形状是否被聚合平均值掩盖。

待核实问题与本次决策

推导 / 教学示例

本候选值得独立分析，原因在于它把一个可迁移到 H20 验证的调度信息问题，与一条不可泛化的专用实现放在了同一改动里。把这两层拆清，比重复“某卡快了多少”更有工程价值。

推导 / 教学示例

仍待核实：H20 目标机器的全部准入条件、main 对应可复现构建、服务接线最终合入状态、真实业务图覆盖、不同模型/TP 的有效形状占比、负载变化下的边际收益、完整回滚演练。上述任一项未满足，都不影响保留原 stock 路径。

推导 / 教学示例

本次建议：进入候选实验清单；不要写成已发布升级指令，不提前兑现 H20 吞吐收益。首个实验的目标应是证明 A/B/C 三条路径确实不同且结果可接受，然后才回答哪一层值得启用。
