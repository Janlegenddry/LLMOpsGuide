背景与概念边界

推导 / 教学示例

推理服务的启动与稳态是两条成本链。启动包含磁盘读取、权重处理、设备内存准备、图捕获和服务就绪；稳态包含请求排队、KV 分配、计算、通信与流式输出。权重缓存只改变其中一部分，不能据此推断首 token、长尾或在途请求恢复都得到改善。

推导 / 教学示例

P/D 分离又引入另一种中间态：请求已经占用 KV 块，数据传输也可以结束，却还没有足够空间进入下一次解码。因此“传输完成”“请求可运行”“服务保持进展”应分别观察。新版本的准入余量处理与既有清零竞争问题属于不同不变量，不能互相替代。

官方事实[3] ↗[12] ↗[13] ↗[14] ↗[15] ↗

硬件边界同样重要。官方 preload 文档限定 CUDA 与 ROCm；这不构成 Ascend 支持证明。SGLang 最新稳定版仍是 v0.5.21，其发布正文 SHA256 与前次记录一致。vLLM-Ascend 的最新稳定版为 v0.23.0.post1，发布于 9 月 22 日；最新 release feed 条目为 v0.27.1rc1，更新于 9 月 29 日，属于预发布，不能与稳定版混为一谈。

机制与执行路径

权重预加载把恢复依赖移到常驻进程

官方事实[3] ↗

固定标签文档说明，每个 GPU 的 daemon 保留后处理、分片后的权重，引擎通过本机 IPC 使用它们。默认 zero_copy 要求 daemon 持续存活；copy 模式另做一次复制。配置指纹或设备不匹配可回退磁盘加载。支持的并行模式包含 TP、EP、DP，但 daemon 启动拒绝 PP；zero_copy 不可与权重 offload 的 sleep mode 混用。量化方法还必须支持后处理权重传输。

官方事实[3] ↗

上述磁盘回退以 fallback 已启用为前提；未命中或 daemon 不可用且关闭 fallback 时，应保留错误边界。copy 模式会复制权重并请求 daemon 释放缓存，不能按 zero_copy 的存活依赖直接描述。

推导 / 教学示例

由此推导，试验对象应是整个生命周期而非单次加载日志：引擎重启时 daemon 是否保留，容器退出策略是否误杀它，版本滚动时指纹能否继续匹配，回退是否被监控。H20 服务可评估这条 CUDA 路径，但本文没有测得任何秒数或容量收益。

KV 准入需要预留成为可运行请求的空间

作者报告结果[4] ↗

#57104 的修复针对 KV Connector 与投机解码组合。旧失效条件中，等待装载的请求可以占满块池，装载结束后却拿不到解码需要的额外块，且没有运行中的请求释放空间。

官方事实[5] ↗

v0.31.0 scheduler 的 _request_remaining_blocks 已加入 _spec_decode_step_blocks，其余量按投机 token 与 lookahead 计算。

推导 / 教学示例[5] ↗

该机制的核心是准入时保留进展条件，而不是等池满后尝试多次调度。

推导 / 教学示例

这是源码核查，不是本地复现结论。建议把“等待请求占用的块”与“运行请求占用的块”分开计量，否则总 KV 利用率接近满载时，无法看出服务仍在计算还是已经失去进展。

多模态参数变成显式信任选择

官方事实[6] ↗[16] ↗

#58830 将非空的请求级 mm_processor_kwargs 与 media_io_kwargs 默认拒绝；可信部署可通过 --trust-request-mm-kwargs 开启。服务端参数和离线 LLM 用法不属于同一变化范围。固定标签安全文档确认这一边界。

推导 / 教学示例

生产侧应先查真实请求。某个历史客户端携带这些字段，即使业务本来正常，也可能在升级后收到错误。把配置迁移到服务端通常更便于统一资源预算；如果必须保留请求级控制，应先确定调用方信任边界，不能为了消除报错一律开启。

生产落地方案

推导 / 教学示例

第一步建立版本证据包。保存容器 digest、wheel 版本与来源、固定源码标识、CUDA 与驱动版本、模型 revision、量化方式、TP/EP/DP/PP 参数，以及实际启用的 connector。版本字符串只能作为索引，不能替代镜像内容核查。

推导 / 教学示例

第二步按服务分组。纯文本单体服务、带外部 KV 的服务、P/D 服务、多模态接口和使用 sleep 的实例分别记录。将本次变化映射到真正命中的代码路径；没有命中的服务无需为不相关特性承担变更。

推导 / 教学示例

第三步先处理请求兼容性。对历史合法请求做回放统计，定位请求级多模态参数及依赖旧行为的客户端。错误必须可解释且可归因，不能把新增参数拒绝混进模型精度下降或通用 5xx 指标。

推导 / 教学示例

第四步为 preload 独立准备生命周期管理。就绪检查、正常停止、引擎异常退出、daemon 缺失、配置不匹配和磁盘回退都要覆盖。明确哪些进程与 GPU 内存属于 daemon，哪些属于引擎。

推导 / 教学示例

第五步执行受控灰度。优先选低风险、可回滚的服务单元；P/D 成对记录版本与传输协议。任何涉及 connector 协议的回补都需重新核验双方兼容性，不能把单边替换当成默认安全操作。
