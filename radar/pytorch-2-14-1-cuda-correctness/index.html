1 结论

官方事实[1] ↗[10] ↗

PyTorch 2.14.1 已于 2026-09-30 19:14:48 UTC 正式发布。与 CUDA 推理直接相关的变化，是 CUDA 13.2 Linux 二进制构建更新到 13.2.2，以纳入 NVIDIA 的两项静默错误修复。[S1]

推导 / 教学示例

建议把本次更新作为一次“产物来源核验与分层回归”：先确认服务真正运行哪一个 wheel、哪个动态库、哪份设备代码，再决定需要替换、重编译或重新生成哪些产物。版本号改变只证明部分交付物改变，不能单独证明整条推理路径已更新。

推导 / 教学示例

对 H20 运维，本文最直接的价值是这种核验方法。不能把 Blackwell 等架构上的 NVFP4 条件直接套到 H20；也不能仅凭编译器缺陷的起始版本，就宣布每个使用 CUDA 12.8 及以后版本的 H20 服务都已受影响。具体 kernel 是否符合触发条件，仍须核对与验证。

2 背景

推导 / 教学示例

一次 Python 调用背后可能同时存在几种不同来源的 GPU 代码：框架自带实现、独立安装的数学库、第三方预编译扩展、本机编译的扩展，以及运行时生成的 kernel。它们未必共享一套构建工具链。

推导 / 教学示例[7] ↗

CUDA 编译会形成 cubin、PTX 等设备产物并嵌入 fatbinary；运行时再为当前 GPU 选择适当映像。[S7] 因而，升级构建机工具链与替换运行机动态库属于不同动作。对于已经嵌入设备机器码的产物，单纯更换旁边的编译器不会重新生成它。这是本文的工程推论。

推导 / 教学示例[6] ↗

PyTorch 的 CUDA 扩展文档要求另外准备编译工具链，允许通过 CUDA_HOME 指定位置，并提供独立扩展构建目录。[S6] “pip 中有 CUDA 依赖”因此不能替代“本次扩展究竟调用了哪个 nvcc”的证据。

3 机制

官方事实[2] ↗

官方 CUDA 13.2.2 勘误描述两条不同错误路径：[S2]

官方事实[2] ↗
  • 编译器路径：自 CUDA 12.8 起，特定至少两层嵌套线程分歧中，编译器省略部分汇合指令可能导致汇合失败及寄存器值异常；单层分歧不在该条目范围。
  • cuBLAS 路径：CUDA 13.2 Update 1 引入的问题可使 NVFP4 输出的矩阵乘忽略 D_SCALE_POINTER；限定算法 ID 66、计算能力 10.x/11.x。
推导 / 教学示例

这两类缺陷都可能让调用正常返回，却产生错误结果。排查时应先区分“生成设备代码时已引入错误”与“调用的库实现处理参数有误”。前者要追溯设备代码的生成者，后者要追溯实际加载的库和选择的算法。把所有质量偏差都归为量化误差，会错过这种区分。

5 取舍

推导 / 教学示例

“全部升级到最新”会同时改变太多变量，导致故障消失却无法说明原因；“只改一个 torch 版本号”又可能遗漏扩展和生成代码。较合理的选择是先建立产物清单，再按受影响层构建最小变更组，最后用完整候选镜像做上线验收。

推导 / 教学示例

保持模型、权重 revision、采样、量化配置和请求集一致，可以减少比较时的噪声，但不意味着逐 token 一致总是适当的数值标准。需要区分算子误差、任务质量与端到端随机性，并在测试前选定参考和容差。

推导 / 教学示例[2] ↗

CUDA 13.2.2 文档仍列有 Hopper 上多次 Grouped GEMM 复用工作区可能挂起或出现启动失败的已知问题。[S2] 因此本文不把这次更新描述为“修复所有 CUDA 正确性问题”，也不把那个独立条目混作本次 NVFP4 修复的触发条件。

6 生产落点

推导 / 教学示例

先在隔离副本建立可回滚的候选镜像，保留旧镜像摘要和旧测试结果。以下是本文建议的操作清单，不代表上游替任何部署完成了验证。

推导 / 教学示例[8] ↗
  • 登记服务框架 commit、torch 完整分发版本、wheel 来源与哈希、依赖锁、GPU 型号及实际计算能力、驱动版本、模型 revision。
  • 记录正在运行的进程加载了哪些 CUDA 库与扩展。不要只看登录 shell 的路径或镜像构建日志；运行时挂载和环境变量可能改变选择结果。
  • 对自编译扩展登记 CUDA_HOME、实际 nvcc 路径和版本、构建日志、目标架构、扩展产物哈希。确需覆盖编译器修复的产物，用确认过的工具链在独立目录重建，再核对进程加载的新文件。
  • 对运行时生成代码分别登记框架、生成器、后端工具和缓存归属。C++/CUDA 扩展 JIT、NVRTC、Triton 或其他生成路径不能只凭“JIT”这个词认定共享同一修复。仅在隔离副本中使用新的缓存目录做冷启动对照；保留旧缓存用于诊断。
  • 驱动以硬件和功能兼容性为约束独立核验。官方 minor-version compatibility 对 CUDA 13.x 列出驱动基线，同时警告 PTX 与新功能存在额外限制。[S8] 不把安装包文件名内的驱动号写成所有部署唯一最低要求。
  • 灰度期间同时观察质量、错误、重启、启动耗时与延迟。若出现回归，回滚成套镜像和依赖，而不是留下新旧库混装的“半回滚”环境。

9 待验证事项

待验证

本次核对已确认版本发布、分发产物和公开修复范围。尚未确认任何特定线上模型、GPU 集群或第三方 kernel 受该缺陷影响，也没有执行本文实验。

待验证

需要实际部署补齐的问题是：服务是否使用 cu132 这一路构建；是否有独立 nvcc 或其他编译后端；旧扩展和缓存是否仍被加载；是否存在满足勘误条件的 kernel；适用库算法是否真正被调用；性能和质量门槛能否在完整服务链通过。

待验证

H20 可沿编译产物和实际 workload 做筛查；NVFP4 条目按其公开架构及算法边界处理。未取得 Windows 对应构建链的同等证据前，本文结论不外推为 Windows 更新保证。需要其他 CUDA 构建或更新分支时，应另核对它们的依赖和勘误，而不是把本次 cu132 的证据直接复制过去。
