SGLang compact verify：元数据归属与错 token 修复

原文 2026-10-06核对 2026-10-09

同一 token tier 的重复捕获可能使用不同设备缓冲，而 replay 只刷新最后登记布局的张量。#42709 已合入 main，v0.5.21 固定源码仍缺少修复。先核对路径、地址与正确性；作者的 Blackwell 早期补丁实验不能外推为最终实现或 H20/NPU 结论。

结论：先核对共享的是哪个布局对象

官方事实[2] ↗[5] ↗[7] ↗

#42709 于 10 月 9 日 02:49:24 UTC 合入 main；v0.5.21 固定标签的捕获函数仍缺少新增复用 guard。main 修复与稳定版交付分开核对，用户镜像是否回补须查看实际产物。

推导 / 教学示例[3] ↗[5] ↗

本次最重要的运维判断不是哪种 GPU 更快，而是 replay 写入的元数据与图执行读取的元数据是否为同一组持久张量。若二者脱节，进程可以存活、图可以正常 replay，输出却失去正确的请求边界。仅监控 CUDA error、HTTP 成功率或吞吐无法排除这种错误。

推导 / 教学示例

建议先确认服务是否使用 compact ragged verify，是否对同一 token tier 捕获多个变体或流，再确认后端是否直接在图内读取布局。只有完整路径证据才能说明本次风险与某个部署相关；不应把整个 SGLang 或所有投机解码都列为已确认受影响。

背景：token 总数相同，不等于请求边界相同

推导 / 教学示例

Ragged verify 把不同请求的验证 token 打包在一起。一个 tier 决定图能处理的总 token 桶，而每个请求实际贡献多少 token，还需要长度与前缀偏移描述。两个批次可以落入同一个桶，却拥有不同的请求切分。如果仅复用计算图而忘记正确刷新其读取的切分信息，计算形状看起来合法，语义仍可能错误。

推导 / 教学示例

这类问题与“图没有更新任何输入”不同。更新确实发生了，但只发生在注册表里最后留下的布局对象所拥有的张量上。早先捕获的图固化的是另一组设备地址，所以日志显示 staging 已完成也不足以证明所有变体都使用新布局。排查要同时记录 Python 对象的张量归属、设备地址和数值内容。

作者报告结果[1] ↗

PR 作者指出 PD-mux × TRT-LLM MLA 的图内读取路径直接暴露；DSv4.1 当前后端有图外复制，其 A/B 另加 #40567。不能仅凭多变体宣布故障已触发。

机制：捕获地址与 replay 更新必须闭合

官方事实[3] ↗[5] ↗

旧函数逐次创建布局并覆盖 num_tokens 登记；staging 从该登记对象取张量并复制 live 长度与偏移。新提交先查已有布局并返回它，因此同 tier 的重复捕获取得相同张量设备地址，staging 也更新这组张量。各 tier 仍独立。

官方事实[3] ↗

未启用 ragged verify 或测试强制 uniform capture 时函数直接返回。后者是测试控制，不能未经模型与后端验证就当生产缓解开关；staging 的 padding 与复制逻辑未被此次重写。

推导 / 教学示例

必须区分三层身份：tier 键、持有张量的 Python 布局对象、CUDA graph 捕获的设备张量地址。注册表指向正确键不等于旧图自动重绑定地址。复用布局对象让重复捕获取得同一组设备地址，replay 无需遍历所有历史副本。局部不变量是“每个 tier 的各图使用同一组会被刷新的布局张量”，不是证明跨流的一切并发写读都安全。

取舍：风险相关性与硬件边界

推导 / 教学示例[3] ↗[5] ↗

H20 部署应按 CUDA 执行路径判断相关性，不能只因显卡同属 NVIDIA 就搬用 SM120 实验结果。模型、注意力后端、graph 变体、PD-mux、draft 参数及请求长度分布都会改变触发条件。NPU 需要另行追踪实际图运行器与元数据路径；本补丁没有给出 Ascend 端到端结论。

作者报告结果[1] ↗

作者称其两组构建的 eager verify 均正确；这仍只是作者试验条件下的结果。

推导 / 教学示例

eager 路径可作为隔离对照，但是否可临时使用、代价多大、如何配置，应由当前部署所支持的启动参数验证。不能把上述结果转化为所有负载都可无成本停用图。性能验证应在正确性通过后进行，避免以更高吞吐掩盖错 token。

推导 / 教学示例

共享对象减少重复捕获产生的元数据副本，但不据此估算显存节省或吞吐提升。跨 stream 的更新与消费次序应作为单独实验维度；本次代码改动的最小性不等于外围调度与后端交互已经被穷尽。
