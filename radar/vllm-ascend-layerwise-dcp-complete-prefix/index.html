vLLM-Ascend layerwise DCP：命中一个前缀，必须拿齐所有分片

原文 2026-11-07核对 2026-11-16

解读新合入的 Mooncake layerwise standalone DCP：键命名、保存者选择和 PP×DCP 完整性必须一致。给出拓扑边界、原始 NPU 结果限制与上线前验收矩阵，不把合入当发布。

推导 / 教学示例

本次最值得学习的是命中判定的单位：一个逻辑前缀块可由多个模型阶段、上下文分片和保存头分组共同组成。若只看到其中一片便减少计算工作，调度器和设备实际拥有的数据就可能不一致。DCP 支持因此不是多加一个并行参数，而是让键、保存责任、命中集合和恢复范围遵守同一份布局契约。

推导 / 教学示例

建议先在隔离 NPU 环境验证状态完整性，再决定是否进入候选镜像。本文没有 NPU 实测、没有安装软件，也没有修改线上配置；H20 属于不同硬件和引擎适配路径，不能据此宣布收益。

背景：三个“并行”不代表同一种切分

推导 / 教学示例

PP 把模型层分给阶段，DCP 把解码所需上下文分给同组设备，PCP 则涉及预填充上下文切分。共享 Store 是状态复用设施，不等于请求一定采用 P/D 分离部署。讨论是否可恢复 KV，必须同时知道层范围、上下文范围、cache group 和头分组；相同 token 哈希不足以描述物理布局。

作者报告结果[1] ↗

作者给出的 NPU 数据是 PDMix：GLM-5.3-W4A4C8-MXFP4，8 卡，128k 输入、1 输出，64 请求、12 个前缀、并发 12，外部前缀比例 0.9，关闭引擎 prefix cache。TP8+DCP8 下 layerwise 开/关 TTFT 为 36.3265/36.8984 秒。本文不复述表中吞吐字段为 decode 速率：它与极短输出的口径需要进一步澄清。

推导 / 教学示例

这一数据更像长输入缓存恢复路径的观察，不能证明长生成、多轮会话或故障期间同样受益。公平测试至少需要相同总卡数、输入组成、Store 温度、实际可复用 token 和请求到达过程；否则缓存命中变化可能被误记成并行算子收益。

机制：把布局身份、写入责任和完整性连接起来

官方事实[2] ↗

键构造器在 DCP>1 时追加 DCP 大小及 rank；DCP=1 不追加该后缀。查询枚举 PP、PCP（仅对应分片组）、DCP 和保存头分组，不是抽查某一个 worker。

推导 / 教学示例

教学例中四个 KV 对象属于同一逻辑前缀，但不是四份可互换副本。前三片完成而第四片缺失时，返回 miss 是保守且必要的选择。把“对象数增加”理解为四倍冗余会误导容量规划；应分别计有效 KV 字节、对象元数据、分配碎片和传输会话。

官方事实[4] ↗

worker 对 standalone DCP 校验本地 rank 等于 tp_rank % dcp_size。保存者按 head 与 DCP rank 的组合去重，而非简单沿用 tp_rank % put_step == 0；相同头分组内不同上下文片不能被误当副本跳过。

推导 / 教学示例

这相当于为每个布局等价类选一名写入者，而非为全部相同头选一个写入者。头相同但上下文范围不同仍是不同数据。诊断“命中一直偏低”时，既要查 Store，也要确认是否有应保存的分片从未产生对象；盲目扩大 Store 容量不能修复缺失保存责任。

测试中的异址恢复比单纯“读回成功”更有解释力：写入与恢复使用不同块位置，可以观察是否错误绑定原槽位。仍需真实设备回归，因为 CPU mock 没有证明计算流、传输流和 allocator 生命周期之间的同步。

取舍：更严格的准入是功能的一部分

官方事实[3] ↗[9] ↗

backend 拒绝 PCP+DCP、与 KVPP 的不支持组合、put_step<DCP 以及 DCP 下显式 prefix_match_unit；组校验拒绝非 DCP 分片、滑窗、循环或 recurrent 状态，并要求最小块大小整除其他块大小。

官方事实[6] ↗

开发文档要求两端 TP/PP/DCP 及 PP 分层一致，GQA/MQA 需 TP//KV头数≥DCP；混合 cache group 的支持不能理解成任意混合注意力模型均可用。

推导 / 教学示例

这些拒绝比“尽力运行”更容易交付：启动阶段暴露布局冲突，避免业务请求进入后才发现缺片。不过严格相同拓扑也限制弹性：缩放 TP 或 DCP 后不能假设旧缓存自然兼容。应把缓存代际、命中恢复速度和备用容量纳入扩缩容设计。MLA 与 GQA 的物理组织不同，应分别用真实模型验证，而不是用一种 roundtrip 代替全部。

推导 / 教学示例

运行台账应同时保存模型 revision、量化、vLLM 与 Ascend commit、镜像 digest、驱动/CANN、Mooncake 版本及所有并行参数。对象命中、已载入 token 和可用于计算的 KV 是三个不同观测点。告警应围绕持续缺片、载入失败和无进展时间，不只看全局命中率百分比。

推导 / 教学示例

先选择可证明的版本和合法拓扑，再做恢复正确性，然后评估性能。即使平均 TTFT 更低，只要出现缺片误命中或质量退化，就不能用速度抵消。发布验收还需等实际发行版本、锁定镜像并检查其依赖，不应在未知依赖上直接 cherry-pick 后宣布兼容。

待验证：发行、硬件和负载仍有边界
