结论：原子的是入队发布，不是远端数据事务

推导 / 教学示例

在传输系统里，返回失败最危险的含义不是“什么都没做”，而是“做了一部分但调用者不知道”。若上层据此立即重试、释放源缓冲或把目标位置分配给另一请求，隐蔽的旧工作可能造成重复写、错误数据或生命周期冲突。首先要问失败发生在设备提交之前还是之后。

官方事实[1] ↗[2] ↗[3] ↗

本次主线修复把 UB transport 的逐任务提交改成一次 submitBatch；worker 对完整集合检查后才在队列锁内改变状态和入队。

推导 / 教学示例

采用时应把保证写窄：针对这一调用中新构造的任务，补丁阻止拒绝提交时把已接受前缀遗留给 posting worker。它不把多次请求、多次成功提交或多个远端写入包装成事务，也不承诺提交成功后没有网络失败。

推导 / 教学示例

还有一条独立的正确性链：任务必须先出现在可查询的 sub-batch 列表，进度通知才对外有效。两者解决不同问题，前者防部分放行，后者防通知早于登记；缺少任何一条都可能让上层看到错误的完成状态。

背景：状态标记、队列可见和设备执行是三个时刻

推导 / 教学示例

可以把一次请求列表看成若干 task，每个 task 又切成多个 slice。业务提交的是完整列表，执行器消费的却是单个 slice。两种粒度之间若只靠逐项循环连接，后面一个任务失败时，前面任务可能已经越过不可逆边界。事后调用 cancel 不必然能追回已经发出的设备操作。

官方事实[7] ↗[8] ↗

v0.3.14 的 transport 在循环中先登记单个任务再调用 submit，失败后请求取消；旧 worker 对不能 markQueued 的 slice 直接跳过。

推导 / 教学示例

这解释了为何“加一次 cancel”不足以等价于“从未提交”。它只能依据当时状态尝试终止。对于尚未发布的私有集合，可以在锁内撤回队列节点；对于已经进入 adapter 的工作，则必须等设备相关的完成或隔离证据。两种清理不能混用。

官方事实[3] ↗

冻结实现中，UB 安装完成设置的是 DRAM 到 DRAM 能力。

作者报告结果[6] ↗

作者在关闭 CUDA 的 arm64 ub-mock 配置中报告 69 个 TENT 目标中 68 个通过，并把剩余失败归因于其容器 DNS/NUMA 环境；另报告目标测试重复 50 次及逐项提交的变异负例失败。

推导 / 教学示例

这些结果对控制流回归有参考价值，但不能写成真实 Ascend NPU、CUDA GPU 或物理 UB 链路已通过。本文也没有独立运行那些命令。

原理：把发布边界与可查询边界分别关好

推导 / 教学示例

关键不是提前知道所有错误，而是让错误在发布前仍可收束。预检查先建立候选清单；队列锁内重新判断是否接纳，然后把 slice 标成 queued。这个标记是准备阶段，不是“设备已经收到”。如果中途发现状态改变，已经准备的私有任务需要终结，而不是留下无人负责的 queued 项。

官方事实[2] ↗

workers 在各优先级队列上记录本次新增数；捕获 bad_alloc 或 length_error 后，持锁从队尾撤回这些新增项。posting 的 popPending 也使用 queue_mutex。

推导 / 教学示例

因此撤回的关键前提是消费者还不能穿过同一把锁，而不是队列名字叫“批量”。如果先解锁再删除，消费线程就可能先拿走前缀；如果只清空整个队列，又会误伤之前的合法请求。本次新增数是一份局部账本，它把回滚范围限制在本次提交。

推导 / 教学示例

预检查失败应保留前面的合法 slice 为 initial；但标记后失败通过取消收尾，不是把状态倒退回 initial。复用旧 task 指针重试与重新构造新任务是不同操作，调用方不能假定失败对象没有变化。

官方事实[5] ↗

task 的取消会逐一请求 slice 取消；initial、queued 或 retry-pending 可即时终结，posting/posted 则留待在途尝试结算。

推导 / 教学示例

这种状态机让“在发布前取消”和“设备已经开始后取消”拥有不同语义。本文的原子入队结论只覆盖前者，不能借同名 cancel 推导后者可立即释放 DMA 缓冲。

官方事实[3] ↗

transport 追加新任务后，以 release store 启用共享原子开关；任务回调用 acquire load 检查。随后对本次非空提交补一次进度通知。

推导 / 教学示例

补发不是重复完成。若任务在开关关闭时结束，补发使查询者有机会看到已登记的终态；若任务在开关开启后结束，可能先后收到终态提示和补发提示。正确消费者必须依据任务状态和身份去重，而不是用收到几次通知来累加完成字节。

推导 / 教学示例

测试最有价值的地方是检查拒绝之后的残留，而不只是断言返回码。错误码正确但队列里仍有一个任务，恰恰是这类 bug；只验 EXPECT_FALSE 会把核心问题漏掉。对已有任务也要保留身份和状态，防止把“没有新残留”错误实现为“把旧工作全部清掉”。

推导 / 教学示例

本次核对还把通知写成一个小型顺序模型：分别令完成发生在登记前、登记后启用前、启用后补发前、补发后。四种设定均有可查询后的提示，其中后两种允许两次提示。这只是原创教学模型的结果，模型没有模拟线程可见性、callback 抛异常或真实队列调度。

取舍：整批准入不等于所有失败都没有副作用

推导 / 教学示例

大批次需要在队列锁内处理更多 slice，可能增加提交延迟或干扰其他提交者。是否值得通常要先看正确性，再看吞吐与尾延迟；不能为了更短锁时间恢复不受控的部分发布。必要时上层限制单批 slice 数，但上限应由实际负载测得。

推导 / 教学示例

队列级撤回没有把所有异常改成统一 Status。候选向量、集合、共享开关和 task 构造等分配位于不同位置，不能把对 push_back 异常的处理外推成完整内存耗尽恢复。具体哪些异常传播、调用方如何捕获，应另做故障注入。

推导 / 教学示例

失败清理只针对这次 worker 发布尝试。成功提交以后发生取消、超时或设备错误，远端可能已经发生部分写入；应用如果要求业务原子性，需要自己设计版本、校验、提交标记或幂等协议。那是更上层的责任，不是此补丁已经交付的功能。

推导 / 教学示例

进度开关不意味着 sub-batch 支持任意线程同时 free、submit 和 query。开关解决的是生产者主动通知的先后顺序；对象生命周期和外部调用并发仍要遵守接口契约并单独验收。

官方事实[9] ↗

官方 Latest 在本轮读取时仍是 v0.3.14，发布于 2026-11-03；#5274 是之后的 main 合入。

生产诊断：为提交身份建立三本账

推导 / 教学示例

建议日志最少能关联 submission ID、task ID、slice ID，再区分准入账、设备尝试账和业务账。准入账回答本次是否发布；设备账回答是否真正开始与结算；业务账回答使用者是否接受结果。三者不能共用一个 success 布尔值。

推导 / 教学示例

A/B 首先使用修复父提交和固定合入 SHA，而不是两个浮动 main。固定编译器、Debug/Release、UB mock 或真实 provider、CPU/NUMA、线程数与批大小。负例中旧实现必须能出现部分准入或通知窗口，否则新实现不出现问题也不能说明负载覆盖了缺陷。

推导 / 教学示例

真实链路验证不能用通过 CPU mock 代替。若实际目标包含 NPU 或 GPU 内存，先确认该内存路径本身受到当前 transport 支持，再安排独立数据面实验；不要把 DRAM 到 DRAM 用例自动改写为 HBM 通信成绩。
