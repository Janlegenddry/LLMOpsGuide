vLLM Ascend：缓存查询失败，调度权何时归还

原文 2026-10-08核对 2026-10-14

#18017于10月14日合入main，将AscendStore查询异常转为零命中并重建失效客户端。用协议状态、发送/接收时限和线程寿命解释活性边界；提出910故障矩阵，不将一秒recv超时等同整体恢复。

推导 / 教学示例

值得关注的判断不是“缓存现在不会出错”，而是缓存查询失败后，调度权是否归还给引擎。外部KV应当是可以拒绝的一份计算优惠；如果等待优惠的控制消息占住唯一推进路径，缓存故障便扩散为整个实例无进展。将错误转成零命中，可缩小这条扩散链，但重算所需的算力、尾延迟与服务端恢复仍要单独付账。

推导 / 教学示例

不要把1000毫秒配置改写成“一秒自动恢复”。它限制接收操作，不覆盖send、序列化、处理线程被卡住、下一轮调度或重新生成。修复建立的是若干局部退出条件，完整请求的进展保证仍需故障注入验收。

背景：查找缓存也会形成全局等待

作者报告结果[7] ↗

原issue #17923报告来自代码检查：服务端处理函数抛异常可能越过回复，scheduler的同步recv没有超时。作者明确问题属于ZMQ控制路径，不需要NPU才能复现。因此不能将这个报告写成所有910集群已发生的存储硬件故障。

推导 / 教学示例

一个常见误区是只看数据传输：KV写入是否完成、内存是否可释放。实际上，确认“有没有可用KV”的前置查询也会阻塞调度。它传输的数据很少，却握有决定后续工作能否入场的权力。少量字节不代表低风险；关键变量是等待发生在后台线程，还是下一次schedule之前。

官方事实[3] ↗[4] ↗

固定入口限定为非layerwise外部lookup，由worker rank 0提供服务。本地已覆盖前缀和不足传输粒度等请求可跳过查询。

推导 / 教学示例

部署边界应写成“具体AscendStore连接器与分支”，而非“Ascend全栈”。H20使用SGLang的主力服务不会直接走这个NPU连接器；可借鉴故障隔离方法，但不该因此要求H20升级或套用延迟结论。910B/910C也必须记录具体CANN、torch-npu、vLLM与vLLM-Ascend SHA，名称相近不能代替调用路径证据。

机制：协议状态、客户端寿命与服务线程是三件事

作者报告结果[10] ↗

ZeroMQ的REQ/REP依赖请求与回复交替。在这个约束下，已经收取请求后发生处理错误，与根本没有成功收取请求，不能用同一种“总是回复”处理。前者可以补一个协议允许的零命中；后者强行send可能是在错误状态上再犯一次错误。

官方事实[4] ↗

服务端接收失败退出，handler失败答零命中；poll观察关闭标志，finally清理。close有界join后仍活跃则警告。

推导 / 教学示例

客户端失败后先关闭，再允许下一次新建。这相当于废弃一张“还欠上一份回复”的对话凭证，而不是在旧对话上盲目重发。新socket可恢复合法的协议起点，却不能让已死亡的服务线程复活。由此可导出两个不同指标：客户端重建成功率与后续有效命中率，不能只取前者作为恢复证据。

推导 / 教学示例

教学成本模型：故障附加等待约等于各次失败查询耗时的总和，再加重算和排队时间。这是责任分解，不是可以直接相加的并发性能预测。若每个新请求都重复支付接收等待，单次有界仍可能使一个观察窗口几乎无有效产出；是否需熔断或退避应由实验决定，本补丁没有证明这些机制已存在。

推导 / 教学示例

源码、测试和协议文档之间形成的是可检查的解释链：调用点会同步等回复；协议要求合法交替；补丁在能答时答，在不能答时让客户端退出并失效。这个链条足以把研究聚焦到RPC活性，却不足以对任何一次线上hang给出唯一根因。

取舍：用重算换活性，容量预算仍须成立

推导 / 教学示例

返回零命中是保守选择：宁可多做一次计算，也不凭空宣布外部状态可复用。代价是高命中业务在存储退化时可能突然增加prefill工作。实例活着，不代表仍能承载同样流量；容量规划应同时准备“有缓存”和“缓存信用消失”两种服务曲线。

推导 / 教学示例[3] ↗[9] ↗[11] ↗

ZeroMQ文档把RCVTIMEO与SNDTIMEO列为两个独立选项。固定客户端只新增前者；核读PR所列vLLM提交的make_zmq_socket，也未见为此REQ/REP路径设置发送超时。因此“一秒内整个查询必返”不是当前证据支持的承诺。

推导 / 教学示例

该实现没有新增错误码来区分业务上的真MISS与故障降级MISS，这有线协议兼容的好处，却会使只看命中率的监控混淆原因。建议在服务日志/指标层区分真未命中、handler失败、超时失效、发送/接收错误与重新命中；不需要把真实提示词或哈希内容写入日志来获得这些信号。

推导 / 教学示例

关闭时有界join是让调用方继续退出的办法，不等于后台线程和所有存储资源已同步停止。如果处理器仍在卡住，继续释放它可能访问的外部资源，需要其他生命周期约束。本文不提出跨线程强制关闭的捷径，也不把警告当作已完成清理。

推导 / 教学示例

错误升级路径应按最小扰动进行：先在隔离环境固定二进制身份，再做可控异常与后续健康请求；若客户端恢复而服务线程已结束，应按现有实例恢复策略处理，不把每次建新socket当成修复。若需要新增熔断、线程监督或强制终止，属于另一项设计，必须明确状态所有权与退避。

推导 / 教学示例

回滚也要带着故障条件验收。恢复旧版本可能恢复已知无限等待窗口；若必须回滚，优先使用经过验证的“不走此外部查询路径”的部署方案或流量隔离，而不是只将镜像换回去。这里没有假定某个开关在所有模型/后端可用，需在目标配置上验证。

实验：先证明故障后能推进，再测性能

E0 身份与路径固定镜像digest、两仓SHA、NPU栈；确认非layerwise lookup实际命中未进入目标路径则停止，不能把无效故障注入计为通过待验证

E5 关闭与资源空闲关闭、处理中关闭、handler持续阻塞，反复启动关闭join耗时与资源最终回收分开记录；线程/context稳态不持续上升待验证
E6 910现场具体910型号、真实存储后端，长短前缀与并发分层结果正确、无跨请求数据混淆；报告完整栈与拓扑，不外推H20待验证
E7 对照与回滚旧版本/新版本同负载，含关闭外部缓存的合法参考配置正常流量回归与故障流量退化预算，所有阈值事先约定待验证
推导 / 教学示例

至少保留逐请求时间戳与成功结果，不能只取平均TTFT。故障窗口中超时后被客户端取消的请求仍在分母里；否则“剩下的成功请求更快”会掩盖可用性损失。完成数、失败数、在途数和取消数应能对账。高并发测试要同时看最长无进展间隔与后续健康请求的完成时间。

推导 / 教学示例

SLO有效吞吐应定义为在规定延迟内成功完成、且满足正确性条件的请求/输出token，按测量窗口计量。命中率变化只解释成本，不单独作为成功门槛。若同一故障导致全局停止推进、资源持续增长或回复串线，应停止推广；性能改善不能抵消这些失败。
