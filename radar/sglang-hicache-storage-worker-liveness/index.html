先确认下一项工作还能完成

官方事实[1] ↗[2] ↗

推导 / 教学示例

值得关注的是可用性的第二跳：某次缓存读取失败并不罕见；危险在于它是否让后续健康请求也失去完成路径。对使用 HiCache L3 的 H20 服务，本次应优先安排隔离故障演练，而非因 main 合入立即改线上镜像。未启用外部缓存存储的实例不应仅凭本文更换配置。

推导 / 教学示例[8] ↗

应与 #43562 分开理解：前者讨论 PD decode 的恢复状态及准入预留怎样共同结算；本篇讨论存储后台工作如何在异常后继续产出协议所需的完成通知。二者都可能表现为等待或集合通信卡住，但不能互相替代。修了后台线程，不等于修了 decode 准入；修了 decode 投票，也不保证存储线程永远存活。

缓存失败通常可重算，通知丢失却会拖住别人

推导 / 教学示例

外部缓存是一项可选加速：拿不到缓存时，理想退化是用更多计算完成同一个推理请求。后台线程则承担另一种责任：它必须告诉控制侧，这项工作究竟结束了没有。数据路径的“没命中”和控制路径的“没有消息”是不同状态。前者可以推动调度继续；后者可能让所有人继续等待。

作者报告结果[1] ↗

作者报告在单 rank H200、文件后端上注入截断读和写异常：旧路径之后的工作停滞，新路径能继续处理健康预取或交回备份确认。它提供了明确的局部验证线索，不是 H20、TP/PP 或真实网络存储的结果。

推导 / 教学示例

可把缓存操作拆成三份账：数据有没有拿到；操作是否已退休；哪些资源可以回收。线上只统计命中率会漏掉第二、三份账。即使 HTTP 最终超时，真正的第一处故障也可能是后台线程早已退出，而不是模型计算或网络设备先出问题。

推导 / 教学示例

原创例子：甲请求读一个坏对象，乙请求随后读一个健康对象。若甲只被记为未命中，乙仍能前进；若甲使负责两者的线程退出，乙甚至不会尝试读盘。此时增加乙的超时或把并发降到一半都不解决缺失的执行者。

失败也有协议，确认也有不同含义

官方事实[3] ↗

固定控制器源码中，查询异常转为零命中；主数据传输异常将本批命中置零，但剩余批次仍生成 ACK。备份包装器记录异常后返回，外层继续入确认队列。它不是重启已死线程的监护器，也未在此新增后端熔断。旧实现外层 finally 仍发送 completed_req；这条最终通知不能替代缺失的中间批次 ACK，所以不能描述为旧实现完全没有消息。

官方事实[4] ↗

Hybrid sidecar 读取异常保留空命中结果并发送通知；相关读操作还有前置处理不在新增异常捕获范围内。因此不能宣传为“任何缓存异常都不再杀线程”。

官方事实[5] ↗

固定的 UnifiedRadixCache 消费备份确认时，buffer 模式释放 staging；其他路径解除记录中的 host 锁。正常队列排空数量经 MIN 归约，且备份统计读取 completed_tokens。确认到达不等价于所有数据成功持久化。这里的 completed_tokens 只累计成功返回的完整批次；失败批次可能已有部分写入，真实持久化对象须独立核验，不能把该计数当作精确落盘字节数。

推导 / 教学示例

最有用的设计区分是：完成通知负责收回控制权，成功计数负责描述得到多少数据。失败时没有通知，会泄漏等待关系；失败时把通知伪装成全量成功，会污染数据事实。运维的任务是同时核对这两个维度。

推导 / 教学示例

多 rank 环境还多一个配对条件。每个 rank 发出三次 ACK，不自动证明三次都对应相同请求和批次。集合通信通常按执行顺序配对，而不是替你校验业务身份。因此实验必须记录 request、operation 和 batch 序号，不能只看队列长度一致。

不让线程退出，可能把故障转换成更贵的推理

推导 / 教学示例

把读取失败作为未命中处理，通常会增加重算。对用户可能表现为 TTFT 上升，对系统可能表现为 prefill 压力增加；若只看最终成功率，缓存后端持续失败会被掩盖。验收必须同时有成功率和代价上限。

推导 / 教学示例

写失败后交回资源，避免把有限 host 空间永久锁住，但下次请求可能无法享受预期的存储命中。不能把备份确认计数用于推导持久化吞吐，应将尝试量、实际成功量、失败量和资源释放分别计量。

推导 / 教学示例

错误日志也会成为负载。若后端长时间故障，每次尝试都记录堆栈，服务可能在“线程活着”的同时消耗大量日志 I/O。不要凭空声称补丁包含限流或熔断；应该在隔离测试中测量持续失败时的日志速率与重试放大，再决定是否需要外围保护。

推导 / 教学示例

还有一个可靠性边界：抛异常不总意味着后端已停止写缓冲区。如果某插件在异步工作未退出时就返回错误，立即复用同一块 staging 可能造成竞态。这是拟验证的连接器契约问题，不是本文已发现的现存漏洞，也不是从该补丁本身就能推导的事实。

待验证

不建议为验证本补丁而同时打开新缓存层、切换模型、改变 page size 和升级通信库。变量过多会让收益与回归都无法归因。

把第一次失联的位置记录下来

推导 / 教学示例

建议观测采用操作级时间线：入队 → 后端开始 → 返回/异常 → 本地 ACK 入队 → 归约/排空 → 锁与页释放 → 下一项健康工作完成。各阶段记录匿名 operation ID、rank、路径类别、批次序号和资源 generation，避免在日志里输出真实提示词或缓存内容。

推导 / 教学示例

三个原创诊断假设：

推导 / 教学示例

1. 执行者退出：某次异常之后不再出现同线程后续操作开始。它与“仍在执行但后端很慢”不同。检查线程活性、队列年龄、最后开始/完成时刻，别只看瞬时队列深度。 2. 通知配对失败：worker 仍工作，本地队列却出现不同操作顺序或缺少中间批次。即使队列总长相同，也应先核对身份序列，再分析集合通信等待。 3. 资源结算缺口：操作已确认，host 锁或 staging 使用量却没有恢复。应检查确认消费路径和 operation ID 的对应关系，而不是把它再次归为后端读写失败。

推导 / 教学示例

区分控制面确认与数据面成功后，可设置两类面板：完成路径面板看队列年龄、线程活性、未退休操作及资源债务；数据路径面板看读写成功量、miss、失败类别、重算代价和延迟。指标名称是本文建议，未声称框架已直接提供。

待验证

只有上述证据指向本变更覆盖的路径，才适合评估定向摘取。若现场是进程退出、C 扩展崩溃、通信 timeout 或 sidecar 前置处理报错，本次异常捕获未必适用。
