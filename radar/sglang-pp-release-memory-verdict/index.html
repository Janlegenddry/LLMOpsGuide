SGLang PP 显存释放：首阶段答应了，不代表所有卡都交出来了

原文 2026-11-12核对 2026-11-13

主干修复把显存释放回复延后到 PP 判定回环，并先在 TP 内统一空闲决策。它消除过早成功和不一致拒绝的两类风险，但不提供跨阶段事务回滚，也不能把 H100 作者测试直接当作 H20 或 NPU 保证。

推导 / 教学示例

当推理与训练轮流使用同一组 GPU 时，释放接口的成功回复就是调用方可能开始下一次大分配的信号。这个信号若只代表首个 PP stage 完成，而后续 stage 还握着权重、KV 或图资源，接口层面的成功就会变成另一进程的 OOM。正确的完成点应覆盖本次请求涉及的整个流水线，而不只是最先收到请求的节点。

官方事实[1] ↗[2] ↗[3] ↗

11 月 12 日合入的 #49798 为这一控制边界补上两层约束：阶段内 TP 先统一决定能否释放，阶段间 PP 汇总所有判定后再由首阶段回复。主干实现有固定提交可审计，不能把合入日期当作 wheel 或镜像的发布日期。

推导 / 教学示例

最重要的保留条件是：拒绝表示本次整体交接没有成立，不表示什么都没有发生。该补丁没有把各 stage 的释放改成先准备再提交的分布式事务；上游可能已释放，下游随后拒绝。调用方应保留阶段与 tag 状态，不能在 400 后盲目切换训练或假定推理可立即无条件继续。

背景：空闲、释放、回复与可复用是四个事实

官方事实[2] ↗

推理实例的资源不止模型权重。KV cache、CUDA Graph 以及尚未完成的批次和控制请求分别有自己的生命周期。释放接口按 tags 选择资源类型；未指定时处理默认全部类型。释放指定资源并不等价于销毁进程、释放驱动上下文，也不保证操作系统报告的整卡空闲。

官方事实[4] ↗

冻结 scheduler 的普通空闲检查包括 running/last batch、overlap 结果队列、PP microbatch 排空及请求列表等。暂停时可忽略部分等待请求，但仍显式检查等待请求是否持有 KV。健康探针使用的判断范围不同，所以“健康”或“GPU 利用率低”不是本接口能成功释放的证明。

推导 / 教学示例

这篇报告面向需要训练/推理资源交接、权重更新或受控回收的运维流程，不建议把释放接口当作一般 OOM 的自动修复按钮。没有记录哪些资源已释放、哪些请求仍在等待时，反复重试可能只会把故障从显存不足换成状态不一致。

机制：TP 先达成同一决定，PP 再形成最终答复

官方事实[2] ↗

每个 TP rank 将本地非空闲状态编码为 busy，使用 TP CPU group 的 MAX 归约。任何成员忙，所有成员都返回拒绝；否则才进入释放。这样避免一个 rank 提前返回，而其它 rank 随后在组内 barrier 等待不存在的参与者。资源处理后先设备同步，再做 TP barrier，才返回本地成功。

官方事实[3] ↗[4] ↗

首阶段本地成功时保存原请求，不立即答复。后续阶段先完成本地处理，再接收上游判定；若上游已经拒绝就继续传播拒绝。末阶段只在首阶段确实进入等待时回传。首阶段在迭代的发送工作之后接收最终结果，再走原控制输出通路。普通 PP、PD prefill PP 与 PD decode PP 三个循环均加入这一回复步骤。

官方事实[3] ↗

首阶段忙时必须立即拒绝，而不是等待“所有 stage 拒绝”。此时流水线可能还需要首阶段继续迭代，后续阶段才能收到控制请求。首阶段若阻塞等尾部，可能亲手停止尾部取得进展的条件。修复把 first_stage_released 一起向下传，使末阶段知道有没有等待自己的接收者。

官方事实[3] ↗[5] ↗

控制判定单独使用 tag=1，普通对象传输保持默认 tag=0。序列化对象的长度和数据都使用对应 tag。判定异步发送的完成句柄合并到请求转发的等待列表，而不在两个请求处理之间单独等待；原因是下游要先收到请求列表，才知道该收哪个判定。独立标签防消息配对混淆，正确等待顺序防“先等别人消费、却还没给消费入口”。

推导 / 教学示例

这里的 tag 是 CPU 对象控制通信的消息标签，不是 GPU 内存类型 tags。把两者混为一谈会误读并发调用：一个用于分流控制消息，另一个选择 KV/权重/图等释放对象。

取舍：成功更可信，但等待和部分完成必须可见

推导 / 教学示例

成功回复等待更多参与者，会增加控制操作的尾部延迟。这不是一般 decode 热路径的吞吐改进。应比较“真正所有 stage 释放完成的时间”与“调用方收到成功的时间”，而不是把旧版更快回复当作更高性能。旧版抢先给出的时间可能根本不是相同语义。

推导 / 教学示例

TP MAX 消除了已到达调用路径的成员间忙闲分歧，却不保证一个已经失联的 rank 能参与 collective。最终 barrier 和 PP 回环都需要通信与执行进展。新增等待点意味着故障恢复方案更应明确超时、进程健康和整组重建边界，而不是期望该补丁本身提供故障容错。

推导 / 教学示例

后续 stage 在接收上游判定前已经完成本地处理，因此最终拒绝不自动回滚先前释放。对需要原子资源交换的训练编排器来说，补丁改善的是成功应答的真实性，而不是完整事务协议。拒绝后先观察各阶段资源状态，再执行经验证的恢复，不能拿返回码替代状态账本。

推导 / 教学示例

源码接入了 PD 两类 PP 循环，但作者已报告的硬件矩阵不能替代 Mooncake/NIXL 正在传输、取消潮、长上下文和多节点网络故障验证。尤其不能把 API 完成语义扩展成所有外部 DMA 已可靠退休的保证。
