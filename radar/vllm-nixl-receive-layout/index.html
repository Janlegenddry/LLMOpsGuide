背景：一个 KV 块有三套坐标

推导 / 教学示例

以下是本文的原创诊断模型。接收问题至少包含三套坐标：业务上的 token 位置、张量上的 head/token 维度、物理内存里的字节次序。传输系统可能把每个字节都准确送达，却无法替上层判断这些字节最终属于哪个 head、哪个逻辑 token。

推导 / 教学示例

这里的大小比较指连接器实际使用的有效传输块大小，不能仅由启动命令的 --block-size 推算。当 P 的有效传输块小于 D 时，一个 D 传输块可能装入多个 P 子块。此时只校验总字节数，会遗漏子块顺序；只校验 shape，会遗漏 stride；只校验某个头上的值，会遗漏头间互换。混合模型还要增加第四项：这个块属于哪一个 transfer group。

推导 / 教学示例

这也是为什么同质配置的健康检查不足以覆盖异构配置。P=D 的有效传输块大小、单一分组、全部有效的满块，恰好会隐藏多个边界。诊断应从容易暴露错误的非对称条件出发，但每次只改变一项，避免把布局问题、token 配对问题和模型数值差异混为一谈。

机制：局部后处理必须尊重逻辑轴和物理次序

官方事实[3] ↗

固定 utils 源码删除了把 attention view 再假设成旧布局的额外 permute；重组按子块、head、token 的关系完成。跨布局分支先还原内存次序，再解释远端 head-major 子块，覆盖 ratio=1 的布局转换。

官方事实[4] ↗

既有几何同步路径也必须纳入审查：固定 base_worker 的 _sync_block_size_with_kernel 根据 attention backend 选择共同兼容的 kernel block size；必要时以逻辑块/内核块比扩展 num_blocks，并把连接器 block_size 改为内核块大小。命令行请求值、cache-spec 的分配块大小和最终传输粒度未必一致。这是解读本补丁的前置上下文，#58860 没有修改该函数，不能声称它修复了几何选择。

官方事实[4] ↗

固定 base_worker 将分组编号随待处理块携带，只访问该组的层视图；未传输尾段按 token 轴清零。对跨布局开关，仅接受远端 LBHNC 到本地 LBNHC 的指定组合；不支持的布局在握手阶段拒绝。token-major 接收不再无条件重组。

推导 / 教学示例

原创推论：同一个缓存指针被不同分组引用，并不意味着每个分组都可以遍历所有视图。测试必须同时记录组编号、块编号和逻辑范围。否则，在指针层面看似节省内存的别名，可能在控制层面变成重复处理。也不能把“第二次处理后又碰巧恢复”当作正确性保证。

取舍：失败显式化值得保留，但要量化代价

推导 / 教学示例

以下为原创工程分析。握手拒绝将一部分问题提前暴露，运维体验可能从“偶尔输出异常”变为“某些实例不能互通”。这可能降低表面可用容量，却更容易隔离不可交付的计算。评估时应统计拒绝原因和受影响实例，而不是把所有拒绝压成同一个错误率。

推导 / 教学示例

同样，兼容性开关应该附带明确方向。允许 A→B 不代表允许 B→A；允许相同块大小的跨布局，也不代表任意块比例都安全。应把连接器组合当作版本化协议条目管理，每个条目分别记录 CLI 请求块大小、cache-spec 物理分配块大小、backend 选定内核块大小、连接器有效传输块大小，以及各组 token→块映射；同时保存布局、TP、attention backend、分组结构和代码 SHA。不同代码层对 logical/physical 的命名可能不同，应以所属字段与阶段标注，不能用一个笼统“block size”覆盖全部。

推导 / 教学示例

没有证据支持这次修复必然提升吞吐。重排次数可能减少，但端到端成本还取决于搬运、网络、调度与额外测试开销。生产选择应先通过正确性，再测 P50/P99 TTFT、TPOT、错误率与缓存占用。不能用平均速度抵销低概率错误 token。
