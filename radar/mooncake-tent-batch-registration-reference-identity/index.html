Mooncake TENT 批量注册去重：一次物理注册如何承接多份逻辑引用

原文 2026-11-05核对 2026-11-05

解读 #5233 的同批地址去重、引用计数与失败回滚，区分注册生命周期、在途 I/O 和真正可释放的内存。

结论：去掉重复注册，不能顺手去掉责任

推导 / 教学示例

这项修复适合所有需要批量注册内存的 TENT 集成者关注：同一地址范围被多个调用项引用时，底层只需建立一份资源，但每个调用项仍然保留独立的释放责任。若只去重地址而不记住引用数量，第一次注销就可能把其他使用者仍需要的资源撤掉。

官方事实[1] ↗[2] ↗[6] ↗

#5233 已于核验当日合入 main。其最终实现合并同批的新地址范围，保留第一次出现的顺序并增加 ref_count；v0.3.14 对应实现没有这一批内索引。

推导 / 教学示例

它解决的是注册身份和引用账的一致性，不是为所有内存提供自动生命周期管理。一个注册引用归零，与硬件 DMA、异步回调和业务请求都已结束，是不同命题；在没有真实后端验证前，不应把它写成“所有提前释放故障已修复”。

背景：已发布快照看不见本批尚未发布的对象

推导 / 教学示例

批量调用存在两种重复：一是本轮输入引用了以前已经注册的范围，二是此前从未注册的同一范围在本轮输入里出现两次。只查询全局已发布表可以识别前者，却可能漏掉后者，因为本轮准备中的条目还没有进入那张表。问题不是线程一定同时执行，而是读到的可见集合比需要判断的身份集合少了一部分。

官方事实[6] ↗

旧 addInBatch 先检查当前快照。发现与已有范围重复时，它增加既有引用；没有已有重复时，它把整批作为新描述符。两条路径都可能让同批的新重复范围进入 callback 多次。

推导 / 教学示例

原创教学例：批输入是 [A,A]，两个 A 都代表同一 (addr,length)，却是两次有效登记请求。正确账本应是一个底层资源、两个逻辑引用。它与 [A,B] 完全不同，也不能简化成“第二个 A 是无意义输入，直接丢掉”。后续调用者仍可能按两次登记各自执行一次注销。

机制：临时身份表去重，引用数承接所有输入

官方事实[2] ↗

最终实现使用 (addr,length) 的 hash 索引记录新描述符在临时 vector 的位置。首次出现时放入 vector，后续同范围只增加对应 ref_count。索引并不决定输出顺序，vector 保留首次出现顺序；混有旧范围与全新范围时，同一 append 辅助逻辑也用于新范围。

官方事实[4] ↗

注册调用方将新描述符传给选中的 transport。各后端处理完成后，成功路径同步本地 segment 元数据；注册 callback 失败时，tracker 会回滚本次对既有范围增加的引用。这里仍依赖各 transport 的事务与清理约定，不能从 tracker 的成功返回推断所有后端具有相同的失败语义。

官方事实[5] ↗

SegmentManager 通过写入副本后再发布来维护快照；失败的更新不发布新状态。读者可持有旧的不可变快照，这避免把“局部构造”直接暴露为已提交状态，但也说明为什么批内准备列表需要自己的身份判断，不能把已发布快照当作所有正在形成对象的全集。

推导 / 教学示例

从设计上看，修复把三个集合分清：已经发布的资源、本批首次出现的新资源、本批每一个逻辑引用。前两个决定是否需要新增底层登记，第三个决定以后要收回多少次责任。这种拆分比“看见重复就忽略”更可靠，也更容易写出失败路径的可核对账本。

推导 / 教学示例

测试最有价值的不是“通过”两个字，而是明确观察第一次和最后一次 remove 的差别。若只检查最终表为空，就可能漏掉第一次注销已经撤销底层资源、第二个所有者期间失效的窗口。

取舍：精确范围去重不等于任意重叠合并

推导 / 教学示例

本次身份键是地址与长度的精确组合，不是内容 hash，也不是内存区间并集。相同地址但不同长度、部分重叠范围和不同地址的相同字节，不应因为这项修复被当成同一个资源。它们是否允许注册，取决于原有接口与后端约束，不能扩大去重规则来消除表面重复。

推导 / 教学示例

新增 hash 表让本批新描述符的查找平均更便宜，但旧范围匹配仍会扫描快照，发布还会排序。因此不能把整条注册路径宣称为严格 O(n)，也没有本报告测得的吞吐收益。短批次可能看不出差异，重点收益是修正生命周期语义，而不是追求漂亮的复杂度标签。

推导 / 教学示例

引用计数代表登记所有权，不自动记录每个在途读写。调用者仍需维持“有使用者就有有效登记”的约束，并依据实际后端完成语义处理最终注销。若底层清理失败，保留必要资源可能优于强制释放；但长期保留是否形成泄漏也要另外监控。

生产诊断：回调次数与剩余引用应该能对上

推导 / 教学示例

原创故障假设：同批出现重复范围，首次注销后另一个使用者发生访问错误，而最终资源表又看似正常。应在合成测试中同时记录注册 callback 收到的唯一范围数、每个范围引用数、注销回调次数与剩余所有者，而不是只追查最后一次错误日志。真实后端表现可能是错误返回、数据错误或其他症状，不能在缺少复现时统一称为 use-after-free。

推导 / 教学示例
  • 为测试地址设置稳定标签，记录精确长度及每次登记/注销事件；不要把生产真实指针或客户 KV 数据放进公开报告。
  • 把逻辑引用数、底层已注册范围数、在途 transfer 数与元数据发布状态分开监控。
  • 失败批次重点核对原有所有者是否继续可用，以及本批新增引用是否清零；不能只要求全表变空。
  • 注销超时或失败后，先确认资源状态与后端约定，不直接重用或释放原内存。
  • 后续健康请求能继续、数据正确与内存最终可回收，必须作为三项独立验收。

待验证：不把主干修复写成所有部署已安全

待验证
  • #5233 已合入 main；v0.3.14 的冻结源码没有本次改动，用户使用的 wheel/镜像仍需核对实际提交。
  • 没有运行上游 C++ 单测、真实 transport 或 GPU/NPU 端到端实验。
  • hash 索引的平均复杂度不等于整个 addInBatch 路径严格线性，也没有证明性能提升。
  • 精确范围重复之外的重叠注册、跨批异步完成、元数据发布失败和部分后端清理，需要各自的回归。
  • 本篇与此前 TENT 请求/尝试计数及 RDMA 回调保活报告是不同问题：这次改变的是登记范围身份与引用责任，不应合并成一个“已修复全部生命周期问题”的结论。
