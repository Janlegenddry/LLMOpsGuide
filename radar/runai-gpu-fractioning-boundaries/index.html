一、结论：先验收边界，再讨论利用率

推导 / 教学示例

Run:ai 的新公告值得关注，但真正能帮助推理运维决策的，是公开组件允许我们分别检查“谁获得资源”“容器怎样得到限制”“运行时是否执行限制”“观测能否反映事实”。把这四个问题合成一个绿色状态，会使容量规划与故障判断同时失真。

作者报告结果[1] ↗

NVIDIA 于 10 月 13 日介绍全平台开源，并列出可单独采用的 KAI Scheduler、GPU Fractioning Operator、KAI Resource Management 和 Workload Map。 这是本轮新发现，不在已上线 21 条研究记录中。本文选取其中 GPU Fractioning 的可核验路径深入分析，避免把平台公告写成四个项目的宣传汇总。

推导 / 教学示例

建议优先级：面向共享 H20 节点上的小模型、开发或低负载服务，作为隔离环境的候选课题；对已经占满整卡、跨卡协同或严格低尾延迟的主力服务，先建立独占基线。没有证据支持“分片一定省钱”“显存有限额就没有邻居干扰”或“H20 可直接套用默认配置”。

二、背景：资源账本与实际占用之间隔着运行时

推导 / 教学示例

原创场景：一张 GPU 同时部署服务 A 与服务 B。平台给 A 记了 30% 配额，给 B 记了 50%，图表看上去还有余量。但这个账本本身不回答三个问题：A 启动时到底看见哪张设备？A 的分配请求是否受到限制？B 遇到 A 的突发计算时，生成间隔是否仍能达标？

推导 / 教学示例

应区分四类边界：

推导 / 教学示例
  • 配额边界：组织允许某团队占多少资源。
  • 放置边界：调度器把哪个容器放到哪张设备。
  • 执行边界：设备分配和内存限制在容器运行前后怎样落实。
  • 服务边界：共同运行时，各服务的错误、延迟与恢复是否达标。
推导 / 教学示例

前三者的存在不会自动证明第四者。即使内存分配被限制，不同租户仍可能竞争计算和数据搬运路径。本文不把资源份额解释为吞吐份额，更不将某一份额写成保证的 tokens/s。

推导 / 教学示例

另一个容易混淆的点是引擎自己的 KV 内存预算。服务引擎计算可用容量的依据，可能与平台记账方式不同。因此验收必须同时记录容器可见总量、引擎实际申请量、运行中峰值和客户端行为；只看平台上“分了多少”不够。

三、机制：一道限额经过多层交接

作者报告结果[3] ↗

固定 v0.1.7 源码显示，fractiond 在 CreateContainer 路径解析容器注解，构造内存请求/上限环境变量及 MPS 挂载；在有设备分配信息时设置可见 GPU，配置允许时还请求相同设备的 CDI 项。内存注解解析错误且 fail-open 时返回空 adjustment；计算模式错误且 fail-open 时则回退 time-slicing，继续构造调整。正常映射记录是异步的，与容器修改分开。

推导 / 教学示例

这给出一个重要的原创验收推论：注解存在、环境变量存在、设备可访问、限制实际生效，是连续但不同的证据点。应为每个阶段保存独立结果，避免拿前一层的成功替后一层担保。

推导 / 教学示例

如何读机制图：承诺、执行和观测是不同证据

推导 / 教学示例

下面的原创机制图将实际解析分支和运行责任分开；位置不表示时间或性能比例。

推导 / 教学示例

  • 容器创建结果：生成调整、拒绝、空调整或计算模式回退。
  • 执行与映射：运行时交接、驱动、应用和异步映射。
  • 观测与验收：GPU 指标、客户端 SLO、独立验证。
推导 / 教学示例[3] ↗[5] ↗

主执行链与异步观测链承担不同责任。内存解析失败可因 fail-open 放行而没有调整；计算模式解析失败则可回退 time-slicing 后继续调整；两类错误在 fail-closed 时均拒绝创建。metricsd 的观测不能直接证明隔离成立。图是基于固定源码的原创抽象，不覆盖所有异常路径，也不表示实测时序。

五、取舍：显存上限、计算共享与可恢复性

作者报告结果[2] ↗

固定 README 要求 Kubernetes 1.28+，支持 NRI 的容器运行时，r615/CUDA 13.4，container toolkit 至少 1.20.1、device plugin 至少 0.20.1；Operator 默认驱动未必满足。它区分默认 time-slicing 和可选 sm-sharing，并提示部分配置只影响以后创建的容器。

推导 / 教学示例

这些要求意味着试验成本可能来自底层软件栈升级，而不仅是新增一个 Helm release。候选组件的收益必须扣除部署、排障和恢复成本。本文不建议为了通过一个分片演示而改变生产驱动。

推导 / 教学示例

原创选择原则：

推导 / 教学示例
  • 以容量不足为瓶颈时，先确认共享后每个引擎仍有启动与动态增长余量。
  • 以尾延迟为瓶颈时，邻居突发应进入负载模型，不能只做平均负载测试。
  • 以冷启动为瓶颈时，将模型装载、编译、KV 预热分别计时；分片不是这些阶段的同义优化。
  • 以组织公平为目标时，明确分母是显存份额、设备时间、成功请求还是货币成本。不同分母不能混算。
推导 / 教学示例

“限制故障租户扩大显存占用”与“保证另一个租户完全无影响”是不同验收项。前者成功之后，仍需验证后者的错误率和恢复预算。

八、指标与验收：让状态、隔离和服务各自说话

作者报告结果[5] ↗

metricsd 的归一化 SM 利用率按其定义将观测 SM 利用率除以基于内存的份额，并封顶 100；部分信息缺失时使用份额 1。 因而它适合在明确口径下观察，不能被解释成“拥有相同比例的计算保证”。

推导 / 教学示例

原创验收账本建议包含：

推导 / 教学示例
  • 部署身份：chart、镜像 digest、驱动与运行时实际版本、节点 GPU 型号；声明值与实际值分列。
  • 限制证明：目标额度、测试分配规模、结果、是否清理、其他测试租户是否受影响。
  • 观测完整性：有效采样覆盖率、Pod UID/GPU UUID 配对、缺失或归因失败次数。
  • 服务交付：客户端 TTFT、ITL/TPOT、错误率、取消后清理、SLO goodput。输出少于两个 token 的 TPOT 单列。
  • 成本：全部共置服务的有效请求产出、整节点成本与失败/重试成本；不得把账面份额直接当实际节省。
