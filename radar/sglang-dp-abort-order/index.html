SGLang DP 取消顺序：HTTP 200 之后，请求为何还在生成

原文 2026-11-12核对 2026-11-16

主干修复把取消与请求送回各 DP 组的同一工作通道。完整报告区分控制回执、调度终态和资源退休，解释双路径乱序，并给出未执行的 H20 与 PD 组合验收矩阵。

官方事实[1] ↗

这次值得关注的不是吞吐优化，而是控制面顺序。SGLang #50147 于 2026-11-15 合入主干；截至核验仅确认合入，不把它称作正式版本已交付。作者在 DP attention 的特定路由下复现取消丢失，修复将取消与请求放回同一组的有序路径。

推导 / 教学示例

生产判断应拆成三问：取消是否进入引擎，持有请求的调度器是否真正应用取消，资源是否走完安全退休。只看 HTTP 200 会把第一层回执误作第三层完成。应先在隔离环境证明控制顺序与终态，再决定是否升级或回补；不要因症状相似就把现网全部“幽灵请求”归因到这一个补丁。

待验证

本文独立阅读冻结提交中的控制器、接收器、调度器及回归测试。没有在 GPU、NPU 或生产系统运行实验；下文实验矩阵、验收门槛与成本口径均为原创验证方案，不是本站实测结果。

背景：为什么用户已离开，服务还可能继续生成

推导 / 教学示例

流式服务至少有客户端、网关、入口处理、排队、执行、输出缓冲等阶段。断开连接只描述一段链路的状态；它不天然携带模型请求 ID，也不保证后端取消已到达。显式取消则是另一条控制消息，仍有等待、路由和处理顺序。两者可能产生同样的外观：客户端不再消费，但后端继续占用计算预算。

推导 / 教学示例

DP attention 下，请求由某个 DP 组持有。共享一个引擎地址，并不意味着所有请求和控制消息共用同一队列。判断“先请求、后取消”是否成立，必须看持有组实际收到的顺序，而不是两个 HTTP 调用的墙钟先后。

作者报告结果[1] ↗

作者的 GPU 对照使用两张 GB200 与 Qwen3-0.6B；默认控制路由的一组 200 次尝试中，修复前 19 次取消丢失，修复后为 0。此结果是作者在特定排队与取消时机下的报告，既非独立复现，也不证明 H20、PP 或 PD 组合已验证。

机制：不能只改发送端，也不能只改接收端

官方事实[2] ↗

控制器的 dispatcher 为 AbortReq 新增 send_to_all_workers 路由。发送函数只遍历存在且处于活动状态的 worker。修复的关键不是广播次数更多，而是让持有组从自己的消息流收到取消；不存在“发给任意 rank，最后总会一样”的可靠假设。

官方事实[3] ↗

接收器同时把 AbortReq 纳入 work_reqs，并从 control_reqs 排除。这保留工作消息在组内传播的顺序。若只扩大发送范围，后续仍把取消当全局控制列表处理，就可能再次丢掉本组的顺序信息。

推导 / 教学示例

可以用一个完全虚构的时序理解：持有者在轮次 A 取队列时，请求尚未到；另一控制流的取消却已可见。若 A 轮发现“没有这个 rid”就结束处理，B 轮后来到达的请求不会自动记住过去的取消。修复需要建立的是请求登记在先、取消应用在后的局部因果关系，不是让所有机器拥有统一时钟。

官方事实[4] ↗

冻结调度器的 abort_request 会遍历现存请求列表与在途请求；在途请求调用 request_finish，随后沿既有清理路径完成。代码注释明确保留一次 decode forward 的可能性。这个补丁不是新的立即释放机制，不能据此绕过在途计算或通信完成检查。

取舍：修复排序，不承诺零延迟取消

推导 / 教学示例

为每个活跃 DP 组发送取消，会增加取消发生时的小消息扇出；它不是每个 token 都新增控制广播。低取消比例下，平均吞吐可能不敏感；但断连风暴或上游超时重试会集中触发取消，因此应单独测控制队列负载。这里没有可移植的吞吐收益数字。

推导 / 教学示例

取消被归为工作消息后，与同批普通控制消息的相对先后也值得回归。暂停、恢复、批量取消和已完成请求的重复取消，都不应只用单一“取消成功率”遮盖。接口约定、日志记录和调度器执行顺序要一致，尤其不能把暂停窗口中的请求算作已经停止。

推导 / 教学示例
  • 适用性先核对：是否启用 DP attention、实际 attention DP/TP 组、控制广播模式及入口路由。未命中这些条件不能直接套用本案例。
  • 不要把 GB200 的作者复现当 H20 的故障概率。不同轮询频率与排队分布会改变竞态出现率，模型更大并不自动意味着更容易复现。
  • 本报告不改变任何线上参数。不建议未经组合测试就把 local-control-broadcast 当通用临时修复。
  • 未知 rid 的取消、请求重试后新 rid、上游断连未生成取消，属于不同语义问题；本补丁并不建立取消墓碑或跨重启持久化。
