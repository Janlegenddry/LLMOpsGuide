vLLM pause(wait)：排空边界覆盖已占 KV 的等待请求

原文 2026-10-08核对 2026-10-09

vLLM #60572 修复暂停排空漏计异步 KV 等待请求。已占块者继续完成，未占块的排队请求等待恢复；上游测试先用输出证明在途，不是生产 API 的前置要求。修复已合入 main，v0.31.0 固定源码仍为旧逻辑。本文独立验收资源、暂停与恢复，不承诺网络故障下的排空时限。

结论：暂停成功应由资源状态解释

官方事实[2] ↗[7] ↗[9] ↗

#60572 于 2026 年 10 月 8 日 09:33:41 UTC 合入 main，固定提交为 7816afdb259dbb18f9e98d11b05194dd3446d0fa。v0.31.0 的 PAUSED_NEW 分支仍只返回 running 数量；用户镜像回补情况另查实际源码与构建身份。

推导 / 教学示例

本次应优先检查使用异步 KV 连接器、并会调用 wait 模式暂停或休眠的服务。排空的完成条件应围绕已经承担的执行与资源责任建立；“当前没有 running 请求”只是一个调度状态，不能单独代表所有已占资源的工作已经处理完。

推导 / 教学示例

也不能反过来要求暂停把所有已接收请求都跑完。还未取得资源的排队请求与已为异步加载取得 KV 块的请求是两种不同责任。修复后的正确边界，应同时证明该完成的工作继续进展、该留在队列的工作没有越过暂停门。

背景：接收、占块与运行并非一个时刻

推导 / 教学示例

服务端接受请求后，它可能先排队，再为远程 KV 加载分配块，待加载完成后才进入计算。在这个过程中，“等待”并不是资源状态的同义词：有的等待请求什么也没占用，有的已经让块池承担了保留责任。运维上若把二者混入一个 waiting 指标，排空时就很难解释为什么 running 已经归零而缓存操作仍然失败。

推导 / 教学示例

因此建议用两个独立问题描述暂停：第一，是否还允许新工作进入；第二，暂停前已经获得资源的工作如何收尾。一次可靠的生命周期切换需要这两个问题的答案一致，而不是单纯把调度入口关闭。缓存重置、休眠和滚动维护尤其应把这一差别写进验收。

作者报告结果[1] ↗

作者报告旧排空遗漏可能使缓存重置失败、pause 或 sleep 返回 HTTP 500，调度器仍暂停。另一处测试超时来自入队后立即暂停、请求未开始的竞态；恢复前不输出在该情形符合语义。引擎修复承接 #59993，不能把本 PR 日期当首次发现日。

机制：计数与调度覆盖同一排空集合

官方事实[3] ↗[4] ↗

PAUSED_NEW 将 kv_holding_waiting 纳入未完成计数并扣除等待新输入的流式会话，同时允许从持块队列调度。普通 waiting 仅在 UNPAUSED 进入；PAUSED_ALL 阻止等待分支。

推导 / 教学示例

可以用一个双向不变量理解它：若控制逻辑还在等待某类工作结束，就必须保留这类工作的进展路径；若某类工作仍持有排空相关资源，就不能先把控制侧计数置零。只修计数可能把过早返回变成长时间等待，只修调度则可能仍让控制层过早执行后续缓存操作。最终改动同时覆盖这两侧。

推导 / 教学示例

空闲流式会话是第三种边界。它等待的是未来输入，不能凭空运行至结束。如果排空无限等待用户继续输入，维护流程就会被业务交互绑住。这里排除这类会话，只是在定义本次排空任务；不应由此推导它们没有任何资源、已经被删除，或会话状态在任意 reset 后都保持完整。

推导 / 教学示例

同理，本修复没有创造网络完成事件。一个真实连接器如果永远不返回，调度器有正确计数也未必能够完成排空。超时、取消、失败回收和外部维护期限是需要另行验证的故障协议，不能从本次计数修复中得到保证。

取舍：更完整的排空可能暴露真实等待成本

推导 / 教学示例

原先过早判空的系统可能返回得很快；修复后等待真正需要收尾的工作，是语义纠正，不能按暂停耗时变长直接判断性能回退。应拆解控制调用耗时、远程传输等待、剩余计算以及缓存操作成本，再判断哪个环节超过维护预算。

推导 / 教学示例

另一方面，保持队列中的新请求不启动是暂停隔离的一部分。验收若只要求“所有请求最后有输出”，就可能奖励一个错误实现：它绕过暂停门继续接流。因此输出完成率要与请求是否已经持块、何时允许恢复共同解释。

推导 / 教学示例

H20 只提供硬件上下文，不能替代具体连接器、KV 配置、DP 布局及运行版本证据。NPU 即使使用 vLLM 相关代码，也需要确认集成版本和实际调度路径；不能把上游 main 修复描述成 vLLM-Ascend 稳定版已交付。此报告没有量化任何硬件上的恢复时延或吞吐收益。

推导 / 教学示例

pause(wait)、全部暂停以及不同休眠路径的目的不相同。实验应保留 mode 与后续动作，避免把一种模式的结果当成其他模式的服务承诺。不能为了让排空测试通过，就取消所有未结束请求或删除普通等待队列；那改变了任务语义。

推导 / 教学示例

核心通过口径是责任闭合，而不是“HTTP 不报错”或“显存下降到零”。池化系统常保留显存，应该检查哪些块可再次安全使用；控制接口成功也需要用请求状态和后续缓存操作交叉核对。所有阈值应在实验前固定，避免看到结果后移动门槛。

待验证：尚不能下的结论

待验证

本站没有执行 CPU、分布式或真实 KV 连接器测试，作者报告不能替代独立复现。H20、Ascend、用户实际镜像、厂商 backport、特定连接器故障与跨 rank 暂停行为均未验证。固定稳定标签缺少修复不等于所有使用该标签的负载都会失败；需要异步持块等待与暂停时序同时成立。

待验证

本次修复不保证所有传输都在有限时间内结束，不定义全局故障恢复协议，也不证明整个缓存子系统在其他操作下正确。未来稳定版包含关系应按实际固定源码更新；不能仅凭发布时间晚于合并时间断言已包含。
