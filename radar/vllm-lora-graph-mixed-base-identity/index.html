vLLM 混批 LoRA 静默失效：CUDA graph 图键必须保留基础模型身份

原文 2026-11-15核对 2026-11-19

11 月 18 日合入的 #67787 修复一类混批漏用 adapter 问题。报告拆解图键、内核类别与捕获输入的契约，给出逐请求身份验收；不把 main 合入当作正式产物已修复。

官方事实[1] ↗

vLLM #67787 于 2026-11-18 合入 main，修复开启 specialize_active_lora 与 CUDA graphs 时，base 与 LoRA 请求混批可能漏用 adapter 的问题。合入不是正式版本或实际镜像已包含修复的证明；本文不据此建议直接切换生产版本。

推导 / 教学示例

对服务运维，关键不是多一个 CUDA graph 参数，而是建立“请求指定的模型身份与实际执行一致”的验收。单请求能正确回答、HTTP 成功、没有引擎报错，都不能覆盖混批之后是否仍使用正确 adapter。

背景：基础模型请求也参与了图的执行形状

推导 / 教学示例

LoRA 让多个请求共享基础权重，再按请求选择附加参数。base 请求没有 adapter，但在批处理映射中仍有“无 adapter”这个身份。业务视角会把它排除在 adapter 数量之外，内核实现却可能把它计入执行类别；如果图分派沿用业务口径，就会与内核口径错位。

作者报告结果[3] ↗

作者复现使用 RTX 4070 Laptop、Qwen3-0.6B 和 self_cognition_Alice adapter；旧 main 为 9fbe012bd7。混批时丢失 adapter 效果，单独请求及 eager 对照正常。这是特定配置的作者结果，不是 H20、Ascend 或所有 LoRA 服务的普遍结论。

机制：图的身份键与捕获输入必须共同正确

推导 / 教学示例

可以把图键理解为选择预先准备好的执行模板。模板不是只看 batch 大小：如果某个维度决定内核要覆盖多少类请求，它也必须与运行时身份映射一致。少算类别，并不一定触发尺寸错误；它可能让某类计算根本没有执行，这也是为什么成功响应不足以做质量准入。

官方事实[2] ↗

最终 diff 同时调整运行时计数和 dummy 捕获映射。混批在 adapter 数量之外加一个 no-LoRA 身份；纯 base 仍返回零。捕获序列让 adapter 先出现、base 最后出现，避免单请求捕获只含 base 而遗漏 LoRA 内核。

推导 / 教学示例

这两个修改不能拆开理解：只改图键，可能选到内容仍不匹配的捕获图；只改捕获输入，运行时仍可能选错键。通用排查需要沿“请求身份 → 映射 → 捕获类别 → 分派键 → 实际输出”把同一个语义贯穿起来。

官方事实[4] ↗[5] ↗

源码交叉核对：v0.34.0 标签的 lora_utils.py 仍直接返回 active adapter 数量；合入提交 0c4fe70 增加混批 base 身份。因此可确认该标签此文件缺少本次计数修改，但尚未在 v0.34.0 上运行端到端复现，不能把代码差异写成该版本的实测故障率。

取舍：不要用关闭优化代替长期正确性闭环

推导 / 教学示例

eager 路径适合作为隔离变量的对照，不是已经测定成本的通用应急方案。若考虑临时回退，必须先在同模型和真实负载下验证吞吐、尾延迟、显存及容量。关闭图或关闭 specialization 是否可接受，取决于业务 SLO，不能只看小模型复现成功。

推导 / 教学示例

多 adapter 服务的验收还应包含纯 base、纯 adapter 与混合流量。相同请求单独运行正常而混批异常，是很有价值的定位信号，但仍需排除调度、缓存、输入模板和 adapter 装载状态差异，不能仅凭回答风格断言命中这一缺陷。

生产诊断：从返回成功升级到执行身份正确

推导 / 教学示例

原创故障假设：某批流量上线后，总体成功率保持正常，只有 adapter 业务输出向 base 行为偏移。调查时先核对开启条件和构建来源，再把异常请求与当时 batch 的 base/adapter 组合关联，避免只按单个 API 请求排查。
