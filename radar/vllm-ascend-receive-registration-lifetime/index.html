一 本次变化与判断

官方事实[1] ↗[2] ↗

vLLM-Ascend #16461 在窗口内合入 main。

官方事实[4] ↗[7] ↗[8] ↗[9] ↗

核心问题发生在请求取消与异步收取交错时：用户侧结束了请求，接收完成仍承担解除资源占用的责任。因此，接收登记不能跟随请求结束立即消失。此次修改把登记清理移到接收完成输出到达之后。

推导 / 教学示例

这里最值得检查的不是吞吐数字，而是长时间运行后“已无客户等待的请求”是否还占住 KV。建议先核对现场连接器配置和镜像源码，再以取消时序进行对照验收。未确认使用对应异步路径的系统，无需仅因这条变更紧急升级。

三 哪些路径值得检查

官方事实[4] ↗

固定 scheduler 源码在 load_async 为真、use_layerwise 为假时把请求放入接收登记集合。这限定了本文的直接分析范围。

官方事实[5] ↗[6] ↗

连接器默认后端名为 mooncake，后端注册表还列出 memcache、yuanrong。后端列表表明接入能力，并不证明它们具有完全相同的运行配置或测试覆盖。

推导 / 教学示例

对 910 的实际意义是：优先问“现场是否进入这个接收生命周期”，再问“使用何种芯片”。H20/SGLang 不直接运行这段 AscendStore scheduler，不能拿本文当作其升级理由。layerwise、纯同步收取、未启用外部 KV 的实例也不能直接套用复现结论。

四 机制是两种生命周期交错

官方事实[7] ↗

vLLM 核心对仍在等待远端 KV 的取消请求可以延迟释放块；完成输出抵达时，已终止请求才走释放分支。这个行为保护尚未结束的传输所使用的内存。本文核读的核心版本为 PR 正文关联的 8cc9aa5ad350f6f80cf3bebb298d410803ff75a9，不声称它等于所有现场依赖。

官方事实[8] ↗[9] ↗

AscendStore worker 从收取线程提取完成时传入登记集合。线程使用集合交集取出允许上报的完成项，只删除此次取出的项。因此，过早删除登记会让已经完成的接收留在线程集合里，却无法沿正常路径交给核心。

推导 / 教学示例

逻辑时序：

推导 / 教学示例

1. 收取启动，登记包含 r；核心等待远端 KV。 2. 客户取消 r，核心把请求终止，但等待收取结算。 3. 旧实现处理 finished_req_ids 时也注销 r；修复保留 r。 4. 收取线程完成；worker 根据登记选择可上报项。 5. 修复后完成项进入核心，登记清理、延迟块释放各在对应职责中完成。

推导 / 教学示例

这是代码关系推导的示意，未展示 DMA 的真实时序。异常传输永不完成的情形需要另一套失败结算证据，不能由正常完成路径外推。

八 升级操作与回滚门槛

推导 / 教学示例

建议分三步。先用只读检查确认是否存在受关注路径及修复语义；再在固定工作负载下强制产生等待远端 KV 的窗口并取消；最后才考虑小流量部署。避免拿随机取消的通过率代替目标时序命中率。

推导 / 教学示例

建议升级记录中分别填写：取消命中等待态的次数、真实完成次数、核心收到完成次数、待结算请求数、空闲块恢复曲线、错误及重算次数。集合类指标最好保留少量经过脱敏的请求级事件，便于分辨同一请求的不同尝试；不要只保留一个总计。

推导 / 教学示例

回滚门槛可以包括：本来健康的请求受影响、完成后出现重复释放断言、待结算请求持续增加、收取失败无法落入终态。阈值由现场 SLO 与基线确定，本文没有替现场给出任意百分比。回滚也不能主动复用仍被传输使用的内存；应按既有排空、隔离与实例替换流程处理。
